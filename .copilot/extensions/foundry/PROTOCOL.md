Writers keep the host-assigned worktree branch so similar assignments cannot rename two branches to the same feature name. Foundry denies the native `rename_branch` action for writers and their helpers; `rename_session` changes only the display title. The assignment also forbids renaming through Git commands; the extension is not a Git sandbox.

Use [`/foundry brief <idea>`](../../skills/foundry/references/brief.md) to work through the product decisions and confirm the outcome before the brief is written. To run `.foundry/catalog.json`, use [`/foundry start catalog`](../../skills/foundry/references/runs.md#start). The skill resolves the name to the committed path the runtime needs. `/foundry` shows the [commands](../../skills/foundry/SKILL.md#commands); `/foundry plans` lists plan names in this checkout. Confirming a brief does not start workers.

### See what can run in parallel

`/foundry status <run-id>` opens the run's read-only **Work graph**. Arrows go from a declared producer to the assignment that needs its output: solid for a checked input, dashed for a pending one. Select an assignment to see its purpose first, then the declared inputs and consumers. Expand **Assignment evidence** for the scope and evaluator. A fixed grain without an inline task can show the pinned text of its own **assigned specification**. No arrow is inferred from a blocker, a common resource or the words in a task. **Trace selection** isolates upstream and downstream paths, not sibling consumers.

**Assigned** means a writer owns the directory, not that its session is running. **Awaiting binding** means no writer is bound yet; **Launch unconfirmed** means Foundry lost confirmation of the original launch and will not replay it. Owner status reports the same distinction in `writerAssignments` without changing the writable `nodes[].state`.

Press **/** to find work by assignment ID, directory or task. The **Find** tab filters by status; matches are highlighted without changing dependency readiness. Select a result to locate it at a readable scale. Drag to pan, use the minimap, or choose **Fit visible graph**. Narrow panels put the inspector below the graph. Assignments with no visible links remain on the board; the participant view never draws missing private nodes.

Opening **Foundry** directly from the UI needs no input. It shows the newest active run visible to this session, or the most recently started visible run if none is active. If this session has no run, the panel says so; it does not start one or substitute example data. To match the in-canvas hammer in the desktop menu, right-click the installed Foundry canvas, choose **Customize…**, then select **Hammer** and **Orange**. The menu icon is an app preference, not an asset supplied by a personal extension.

The **Run** tab shows diagnostics and charter questions, and for the owner, **Product evidence**: checkpoint, goal result, qualification and timing when known. A pending-call notice names the affected operation. A missing shell reply is neither a failed check nor a reason to launch it again. The graph refreshes while visible, without advancing the run or resetting navigation on every receipt. Without a run, explicitly open the **example dependency map** for a labeled, static example.

## Commit the contract

For a goal run, put the shared requirements in `.foundry/<plan>/journey.md` and omit `boundary` from every squad. Use nonempty UTF-8 text. Foundry puts the full committed brief into each scout's prompt alongside its charter and the goal result, without applying the source excerpt limit.

Scouts also see the names of other committed regular files. A scout can request a file by path, then follow a reference to another file. Each new review of the same version includes the previously requested text. A name alone isn't a citation. If a proposal cites a requested interface, the writer gets its exact revision and path, not ownership of its directory.

Keep trusted acceptance code, helpers and fixtures under `.foundry/`; they can be shared across plan directories. Shared-brief runs pin the entire `.foundry/` tree, so even an unrelated change there on the target requires fresh review. An ordinary source file outside it is not pinned merely because a scout reads it.

Give each squad disjoint writable `areas`, a charter describing its responsibilities, and trusted component `checks`. Existing plans that explicitly list `boundary` for each squad keep their original pins and narrower read scope.

For maintenance, state in the charter when writers may consult their own prior files. A fixed grain or scout proposal uses one `directory` field: `"lib/codec"` selects the accepted copy at kickoff; `"<full commit>:lib/codec"` selects that copy instead. Both write to `lib/codec`. A new unpinned directory starts empty. A pin must name a local commit containing the directory; a missing pin never falls back to the latest copy. Neither spelling grants read access by itself.

```json
{
  "version": 2,
  "id": "catalog",
  "direction": "A customer can find a product and see its current price.",
  "target": "refs/heads/main",
  "productCheck": ".foundry/catalog/invariants.mjs",
  "goalCheck": ".foundry/catalog/customer-lookup.mjs",
  "squads": [
    {
      "id": "browse",
      "charter": "squads/browse.md",
      "areas": ["src/browse"],
      "checks": [".foundry/catalog/browse-unit.mjs"]
    },
    {
      "id": "offers",
      "charter": "squads/offers.md",
      "areas": ["src/offers"],
      "checks": [".foundry/catalog/price-unit.mjs"]
    }
  ]
}
```

Save this as e.g. `.foundry/catalog.json`. Start reads the policy from the activating checkout's `HEAD`, not from uncommitted edits. Resume reads the existing run's pins. `target` is an existing local branch. Integration requires its conserved files to match the approved contract. Changing the activated plan itself needs a separately authorized run; a mixed merge that leaves the plan unchanged can be reviewed on the existing run.

By default, Foundry starts every ready assignment in parallel. Set `limits.workers` to a positive integer to cap concurrent scouts and writers. A writer keeps its slot while its component check runs; product and goal checks do not occupy writer slots. Foundry keeps the cap confirmed at activation: when a slot frees up, the next ready assignment can start without an operator turn. Dependent work waits for its checked inputs. Native helpers inside a writer do not use Foundry slots; Copilot manages their concurrency and permissions.

For an unattended run, `limits.assignments` optionally caps **total** work across all checkpoints, reloads and resumes. Each reserved scout (even in a batch), new writer, or bounded repair costs one assignment, including a repair returned directly to the same writer. Refusal does not refund a reservation. Helpers, verification and retrying or recovering the original call do not count. At the limit, existing assignments and checks can finish. An unfunded proposal does not hold up verification of independent outputs; a one-off still needs every seeded output. `foundry_status` shows `assignments.used`, `assignments.limit` and the blocker. Zero allows verification of an already-good baseline; omitting the bound leaves total assignments unlimited. This is not a credit ceiling. `limits.repairs` separately defaults to one repair per writer output (zero is valid).

`limits.deadline` must include an explicit timezone, e.g. `2030-06-01T12:00:00Z` or `2030-06-01T14:00:00+02:00`. No new work begins at or after that instant. A later turn may still settle and hand off a goal product if both exact, current checks finished **before** the cutoff and ordinary release conditions hold. The runner records completion after verifying the export. Legacy receipts without a completion time, or an older ambiguous deadline, cannot establish timely completion.

`productCheck` tests invariants that a useful intermediate tree must preserve. `goalCheck` tests the whole brief: in this example, look up a product through the customer-facing interface and check the returned price. Confirm that the evaluator fails on an unfinished product, not just that it passes on a sample. Exit **0** when the goal is met, **1** when a required behavior is missing, or **2** when a required external observation is unavailable. Print what is missing. Other exits and infrastructure failures block the run.

Foundry checks the baseline before staffing anyone. If it meets the goal, the milestone evaluator must pass on the same commit before Foundry accepts it. Otherwise, when the goal evaluator knows which squad owns the gap, it can print exactly one `FOUNDRY_SQUAD=<squad-id>` line to stdout with exit 1. Foundry asks that squad first. A missing, ambiguous or unknown hint starts full discovery; if the named squad has no actionable work or its candidate is blocked, the search widens. The hint does not change any charter.

For rolling **scheduling** feedback, the goal evaluator writes one UTF-8 JSON value in place to `FOUNDRY_GOAL_FEEDBACK_FILE` (a runner-owned temporary file outside the product). Leave it empty for no feedback; don't rename a file over it. Foundry retains the exact JSON bytes as a Git blob referenced by the verified receipt. On the next eligible check, read JSON from `FOUNDRY_GOAL_DELTA_FILE`, a read-only temporary file: `{"version":1,"base":"<full prior commit>","head":"<full current commit>","paths":["old/name","new/name"],"previous":{"gaps":["round-trip"]}}`. `previous` is the original JSON value; `paths` is the complete tree diff, including additions, deletions and both sides of renames. `[]` means the trees were compared and had no differences. Only goal checks receive these paths; do not persist them.

The input path is **unset** on a first check, a changed evaluator pin, or when the most recent eligible receipt (same run and pin, exit 0 or 1) lacks usable feedback or its exact diff cannot be obtained. Use normal scheduling then. A legacy evaluator may still emit one `FOUNDRY_GOAL_FEEDBACK=<JSON>` stdout line **instead** of writing the file. For legacy feedback only, Foundry also supplies the old `FOUNDRY_GOAL_DELTA` inline variable when it fits its original 32 KiB transport envelope. That envelope never limits the file or the changed-path count. Neither feedback nor an unchanged path proves a pass: the current candidate must earn its own passing receipts.

Ready writers start without a new activation or user turn. As soon as the admitted outputs are checked, Foundry checks the combined product without waiting for unrelated scouts. A report that adds work before the check settles invalidates that candidate, not its component receipts. If no actionable work remains or the outputs reproduce a previously failing tree, status reports the gap and the reasons; the checkpoint is retained, not accepted as the goal.

### Discover and split work

The run starts without assignments. Foundry dispatches ready charters to a `foundry-scout` workflow. Each scout gets evidence from the exact assessed commit, the goal diagnostic and the relevant graph. The host's prompt window sizes each page, not the total evidence a review may inspect. If a pinned index will not fit, the scout gets a searchable file catalog and can request exact files with `needs-evidence`. A path listing or graph page is not a file citation. Switching to a file and back to a receipt resumes at its first unread unit. Once the receipt has been read, the scout can decide from the evidence but cannot keep repeating the lookup. Explicit operator limits still apply. One slow charter does not hold up the others. A squad's optional native `agent` selects its **writer**, not its scout.

**Research before assigning a writer:** An area charter can opt in with `"researchAgent": "foundry-research"` in the committed squad. The scout can then return `needs-research` with its question in `reason`. The bundled researcher can read source and search/fetch public documentation. To use a connector or disposable experiment runner, name an installed custom agent with those specific tools instead. Describe permitted reference checkouts, pins and services in the charter. A profile is not a permission grant or a sandbox: the host must enforce access and isolate any probe tool. Do not give a researcher broad write or shell access to the product.

An investigation with cited findings goes back to a **tool-less** scout once, even when the overall answer is unknown. The scout can assign independently supported work or leave the question unresolved. Its same-version findings, citations and remaining unknowns follow the assignment to the writer; no other squad's report is included. An unknown result without findings stays unresolved without another assignment or owner dialog. Research and follow-ups consume ordinary assignment slots. Findings are context, never evaluator receipts, proof of completeness, or permission to modify another directory. Existing briefs without `researchAgent` stay packet-only.

Answered research must include cited findings with a source, kind and observation. Foundry does not cap their count or text length.

Each shared repository has one frozen commit per run. A researcher reports `references: [{repo, revision}]` with the sibling checkout name and full commit, even if its inventory is incomplete. Foundry freezes the first commit it can resolve locally in that sibling. An unreadable revision stays in the research report as metadata: it does not reserve the name or wake a waiter. Any squad may confirm a frozen pair; a conflicting report is rejected in full, even if the original checkout has since disappeared. Fresh packets show frozen pairs, not other squads' findings. Free-text citations are not pins.

To wait for or inspect one of those revisions, use `waitFor: "reference:adapter"` (`waiting` for a scout, `unknown` for a researcher). When the commit is available, Foundry dispatches the squad's opted-in researcher, or a tool-less scout if there is none. `waitFor: "coverage"` still means a checked output from that squad. Publishing a pin does not wake an output waiter or start unrelated work.

For a permitted sibling of the product's primary checkout, `foundry_reference` reads regular UTF-8 blobs at its published revision. A reader job has a dedicated workflow. Only its single running direct agent can read, under normal host permissions; neither an agent from a finished attempt nor a peer in the same session can use its review ID. If the SDK cannot identify the running agent and its launch unambiguously, the read is denied. The reader never reads working-tree bytes, checks out another branch or fetches missing objects. An inaccessible blob or an unavailable visual reference is unknown, not evidence.

For example, a browse scout can separate the query editor from the work that actually needs pricing. If an earlier plan still has a never-issued `lookup` assignment, its replacement can look like this (other report fields omitted):

```json
{
  "replace": ["lookup"],
  "grains": [
    { "id": "query", "task": "Preserve the typed query across navigation.", "directory": "src/browse/query", "check": ".foundry/catalog/browse-unit.mjs" },
    { "id": "lookup", "task": "Look up the entered query and display the returned price.", "directory": "src/browse/lookup", "check": ".foundry/catalog/browse-unit.mjs", "needs": ["query", "price"] }
  ]
}
```

Before adding `needs`, name in `reason` **which checked output the consumer needs to start and why**. To add an edge to an existing, never-reserved job, explicitly `replace` that ID and propose its amended `needs`; downstream jobs can keep referring to the ID. An issued job keeps its frozen inputs. In the example, `query` and `price` can proceed independently; only `lookup` waits for both. If a producer hasn't reported yet, propose independent work rather than inventing a dependency. A fixture-backed editor alone cannot satisfy the customer lookup goal.

A saved report rejected specifically for `Unknown required output: ID` does not publish a dangling edge. If the producers later appear on the same reviewed inputs, the owner automatically revalidates that original report once they are all declared. It still must pass every scope, evidence, cycle and grant check. The consumer waits for **checked** pins before dispatch. No scout replay or manual resume is needed, including after an issuer reload. Names in a cycle of unadmitted reports are not producers.

- A split is all-or-nothing. The directories must be disjoint, IDs unique, and the resulting graph free of cycles and dangling dependencies, including other squads' consumers. Use `replace` to remove your own never-started assignments. A scout cannot displace live work, a refusal, an uncertain call or an output awaiting its milestone check.
- For one change that must pass or fail together, use e.g. `"directory": ["codec/decode", "codec/encode"]`. Both complete directories belong to one assignment, candidate, component check and dependency ID. `codec/checksum` can run in parallel; neither writer owns `codec/`. Every root must be in the same charter. A writer cannot acquire or drop individual paths.
- Before dispatch, a fresh review may explicitly replace an untouched broad start with fresh assignment IDs. Its old reservation is recorded as `withdrawn` (still charged to the lifetime budget) and cannot launch later. A prepared manual call, permission hold, approved candidate reuse, repair or issued start is not withdrawable. After a passing product checkpoint, the same split uses the checked tree; an active consumer can defer it.
- A fresh area review can see a `supersededAttempt` when an exact terminal blocked component has lost prerequisite pins. It may explicitly `replace: [oldId]` in a single-grain proposal: a fresh ID, the same directory and evaluator, newly qualified inputs from this packet, and all still-current pins. This is a new assignment, not a retry. The original writer's token cannot submit it, and its candidate and receipt remain in history.
- After a bound writer stops for missing input, a later checkpoint's current area review may assign **different work** to that exact directory and check. On the **same checkpoint**, only an owner-routed `foundry_review` (compare) comparison for that directory can do this, including a review continuing its evidence read. An ordinary same-checkpoint review cannot. The proposal needs a new assignment ID, no live consumers of the stopped assignment, confirmed terminal writer calls and current, qualified prerequisites from the review packet.
- A budget-recovered scout can use this handoff when its original owner comparison names that exact directory, whether it was requested during a pending goal or after an unmet goal. The owner’s next scheduling turn reconsiders a saved overlap from its original report and packet, without replaying the scout. A real conflict keeps ownership in place; look for `reviews[].handoffHold`. A predecessor preview remains a draft in its original worktree and is not an input to the successor.
- A scoped, distinct task can also take over an exhausted component's directory if it needs a newly qualified prerequisite. The failed candidate remains with the predecessor; it is not copied. If a later product has already superseded an overlap refusal and its own goal exited 2, the owner can request a **fresh** comparison with that goal ID and the same offered blob and directory. The prior reviewed directory, cited files, prerequisite pins, evaluator and target must still match. A missing observation alone is not a reason to open arbitrary comparisons.
- The receiving review records its `predecessor`. One new writer gets its own token; it does not inherit the old worktree, read permissions or receipts. If the latest eligible report is already saved as `Writable directories must be disjoint`, a normal owner turn reconsiders the saved packet at its original pins. Do not resend the comparison, reuse the old token or restart the run. The new work still needs its normal checks.
- A packaging writer cannot own a parent directory and depend on a checked child that ownership would retire. Foundry preserves the graph and gives the charter one review of the conflict on that revision, within the ordinary assignment limits. Use a disjoint directory to consume the child, propose a complete replacement, or report `needs-decision` if neither meets the committed layout.
- Each review accepts one result. Replaying it does nothing, and a superseded review cannot change a newer plan. A later checkpoint or a newly blocked or repeated area assignment supplies new evidence for discovery without another operator turn.
- **A checkpoint preserves the tree, not the division of work.** You can request a checked output by ID, or propose new directories and IDs anywhere inside your charter. For example, after `src/browse` passes, propose `src/browse/query` and `src/browse/results` together. An overlapping checked name is retired automatically; `replace` can also retire a checked name explicitly. Old commits, receipts and files outside the new assignments stay intact. Checked names that depended on the superseded version retire with it. Unaffected checked outputs remain available by name.
- If a valid area proposal would retire a version still pinned by a current assignment, the review records the proposal as `deferred` and names its consumers. No assignments or pins change. A queued task that needs one of those consumers can still start and inherit its pins. Once all consumers of those versions settle or release them, the charter gets one fresh review at the current assessed checkpoint, within the normal limits. The old proposal is context, not a plan to replay; only the new report can authorize a repair.
- A refused assignment cannot be retried, but it no longer pins its inputs. A conflict with a moving target is rechecked on participant turns: resolving the edit or releasing its last live input can unblock the run without overriding a refusal.
- If a batch reproduces a tree that already failed the goal, status marks its new outputs `repeated`, not qualified. A scout can use them as checked inputs or propose different work in the same scope. Repartitioning requires their bytes to match a passing product checkpoint. A new ID, report or direct edge to an already pinned ancestor does not restart the same assignment on the same base with the same effective inputs. If a pending prerequisite later resolves to the same input, that never-issued job is marked blocked and can be replaced. None of these cases creates a checkpoint.
- For more text, return `needs-evidence` with exactly one selector shown in the packet: `file` for a pinned path, `receipt` for a goal diagnostic, or `detail` for scoped context such as an owner's question. Add `match` to search for one case-sensitive literal. To find the next occurrence, repeat the search with `offset` set to `hit + 1`; to continue a range, omit `match` and use `offset: end`. Offsets are UTF-16 indices. A miss or a request that makes no progress ends the lookup. Only delivered product-file text can support a file citation.
- `no-gap` requires a complete packet. Every citation must match a text-bearing path and blob ID in the journaled packet. On partial coverage propose supported work, request a file or its next page, or report the missing fact. A duplicate request for already-delivered text gives the charter one decision follow-up on those same inputs, in ordinary discovery or a still-current checkpoint comparison. It does not start another read cycle. Unavailable files, out-of-scope requests and native refusals do not trigger this follow-up.
- Use `waiting` with `waitFor` and `grains: []` if an area charter cannot proceed until another charter has a checked output. Foundry reopens the consumer once per changed set of producer outputs. It still needs an explicit grain dependency to use those files. Use `unresolved` for missing facts: Foundry tries authorized research once if available. Only a `needs-decision` with `ownerInput: "product-choice"` or `"external-action"` asks the owner. The answer is context for one fresh review, not permission to change the contract.

**Fixed contracts:** version 1 retains its committed `grains` (`id`, `directory`, `specification`, `boundary`, `check`, optional `needs`) and squad-to-grain ID lists. Existing runs do not acquire broader authority on resume. For an explicitly requested one-off, use version 1 with `seed` and no `goalCheck`: a passing `productCheck` qualifies that batch. Unseeded version-1 discovery without a goal still reviews changes to chartered inputs on participant turns. A host trigger can wake an existing run, not authorize one.

**Finished writer pool.** For each new batch, Foundry prefers an idle session that previously delivered the same set of directories, then another finished writer from the same squad and run. A finished writer needs a passing component included in a passing product checkpoint; an idle app window, a preview, or a component pass alone does not count. An open repair, uncertain handoff, pending input, or unverifiable native worktree is not available. Availability lookups share a five-second budget for the batch. If nobody qualifies in time, the assignment starts in a new session rather than waiting. Each assignment still consumes one reservation.

Only conversation context carries over. A pooled writer's `workspace` is a fresh detached Git checkout **inside** its native worktree, at the new assignment's generation. Old files (including unsubmitted edits), branch and receipts remain untouched. Git objects are shared; each checkout still uses space for its working files. Queue admission is not a component pass. A lost acknowledgement can be confirmed by the named recipient opening the assignment with its delivered token; do not resend it or create a replacement.

## Run operations

The [checkpoint triage and repair handoff](../../skills/foundry/references/runs.md#checkpoint-triage-and-repair-handoff) is the common owner procedure. A product repository supplies the commands, evidence requirements and ownership boundaries specific to its brief; it need not maintain a second copy of the procedure.

### Choose a Foundry tool

Use the effect you intend, not the fact that a run looks stopped. The slash commands for ordinary operation are unchanged. In the table, names omit the `foundry_` prefix.

| Intent | Native tools and boundary |
|---|---|
| Operate a run | `start` only creates; repeating it does not dispatch. `resume` only continues an existing source. `pause` stops new work. `configure` changes future scheduling, not run authority. |
| Inspect or pass information | `status` reads scoped state, proof, usage, cleanup eligibility or the issuer's permissions. `publish` offers a file without granting access. `reference` is a pinned read for the bound researcher only. The board's `get_snapshot` reads its displayed view, not an arbitrary run. |
| Work inside a writer grant | `workspace` verifies the pooled writer's checkout. `preview` pins draft bytes, `submit` captures a candidate or reports a supported stop, and `claim` proves an *existing* uncertain writer's identity. None substitutes for the others. |
| Direct discovery | `review` starts a comparison or retries an eligible blocked review. `review_note` queues evidence for a later ordinary review without starting one. `attribute` routes a confirmed failed step; it cannot change the verdict. `clarify` reopens a specific lost owner question, not a scout. |
| Change an assignment | `grant` selects one exceptional permission or writer grant. `correct` removes a contradictory clause for an existing writer; it does not grant new reads. |
| Obtain or change verification | `check` requests a new observation. `retire` closes a proven dead legacy runner **without** a verdict. `repin` changes the contract or evaluator under separate approval. |
| Assemble checked outputs | `checkpoint` verifies an independent **non-release** subset. `deliver` admits approved, absent test directories and requires fresh combined product and goal checks. |

### Operating procedures

**Tune a running factory.** The owner's `foundry_status` shows `scheduling.revision`, effective `workers`, the committed `ceiling`, and `checkpointReviews`. Call `foundry_configure({run,revision,workers:2})` to change the cap on new reservations. Use `workers:null` to restore the brief's cap. Lowering it drains naturally: existing scouts and writers keep their reservations. `checkpointReviews:false` stops new pending-goal comparisons, source-backed comparisons after exit 2 and automatic checkpoint surveys, without withdrawing reviews already admitted. A stale revision is rejected; reread before changing it. Neither setting changes the brief, permissions, evaluator, or release conditions. No pause, restart or reload is needed for a policy change.

**Recovery and diagnosis.** Owner status includes the release engine's proposed action, permitted work and reason at the observed target. It does not apply the action. While the runtime is running and observing an issued check, a missed shell notification is recoverable: a changed ledger row prompts a verified receipt read and the normal scheduler reconciles it. An unchanged row, an uncertain call with no receipt, or a permission refusal cannot synthesize a pass or authorize a retry.

A changed conserved contract closes release admission at that target, not work already routed by an automatic survey on an exact passing checkpoint. The owner resumes the existing ledger by source; the original issuer still needs its own permissions. A descendant target does not invalidate that survey's report, evidence follow-up or writer. Components publish against the frozen inputs. A compatible target receives the retained output only through fresh joined product and goal checks. With changed conserved inputs, status names those paths and the separate work target; no result qualifies the merge. Ledger contention backs off the receipt *read*, never the original native call. A stale reader or invalid store stops the observer and logs the error instead of continuing on unverifiable data.

To give one squad historical context, call `foundry_review_note({run,squad,receipt,question})`. Use a **goal check ID** from `foundry_status({run,detail:"proof"}).goalChecks`, not a commit: two evaluators may have checked the same commit. You can cite the full receipt by ID or optionally select a verbatim `excerpt`. Distinct notes can queue for the same squad; resending an identical note is not new work. A note supplies historical context at normal review, not an assignment, permission, a product-file citation, or a fresh verdict.

**Iterate before release.** Send a mismatch to a bound writer only if its task and pinned inputs already cover it. Distinct work in the same directory must wait: a refused comparison is not queued and does not change the binding or its receipts. Once the directory is available, call `foundry_review({run,compare:{directory,receipt,blob,question}})` with the offered blob and the specific change to review. For a settled unmet goal, `receipt` is its check ID. While the goal is in flight (even under a superseded evaluator), use the latest passing `products[].check` from status **for that exact checkpoint**. Do not use a commit, an outstanding reservation, or a historical goal failure as a substitute.

**A new source-backed question after exit 2:** Use the current goal ID as `receipt` and add `source:{commit,file,excerpt}`. `commit` is the full current checked product ID; `file` is a regular UTF-8 production file in this charter; `excerpt` is verbatim at that commit. The operator reviews the question, citation, offered blob and directory. Approval opens one scout review, not a writer or release check. Its first packet delivers the named file or, when it does not fit, a citable range at the excerpt. Only the displayed text is evidence; the scout can request another range before deciding. Only a proposal citing the delivered source can staff the named directory under normal ownership, capacity and checkpoint-review rules. An older build's failure is neither required nor carried forward.

**An unrelated output landed before the report returned.** On its next permitted turn, the owner continues the saved repair without another scout or confirmation, including in Interactive Assisted. Foundry checks the original charter, scope, evidence, prerequisites and evaluators against the new checkpoint on the same target. If any input changed, is unknown, or conflicts with another owner, the repair stays blocked. Earlier declined or unanswered dialogs stay closed to automatic recovery. The original report and product remain in history; no ownership or passing result is inherited.

If the current goal exited **2** and omitted a step that failed on the **same checked product**, compare both receipts explicitly: use the current goal ID as `receipt` and add `historical:{receipt:"<preceding failed goal ID>",step:"<stable journey or step identifier>"}`. Read both outputs first. Foundry rejects a stale pair, an intervening goal, a changed target or product, or a step identifier absent from the earlier output or mentioned in the newer one. An omission is not proof of a defect. The scout receives both receipts and must find support in the checked product before proposing work. A changed repair earns new checks; resubmitting unchanged bytes does not replay the old goal. This does not transfer rolling feedback between evaluator pins.

A pending-checkpoint comparison can finish on that same checkpoint if its goal returns 2 while the scout is reading. If an independent sibling advances the checkpoint first, a component already published from an admitted comparison can still trigger integration under the same evaluator and target. Foundry rechecks the directory and inputs against the new base, and only changed product bytes trigger new checks.

If that component instead fails with exit 1, a normal scheduling turn can return a remaining repair to its original writer. The original failure, writer generation, target and evaluator must match; the directory, checked prerequisites and cited supporting files must still be valid on the newer checkpoint. A submitting writer receives a new token inline; otherwise Foundry sends one repair notice. Neither path starts a replacement session or repeats the failed check.

The scoped review can staff that directory from the unchanged checkpoint and its checked prerequisites. It cannot displace another assignment, bypass permissions or expand its scope. Check for a bound writer; a file offer, queued note or review ID alone means no implementation has started. Component work and a midpoint comparison can proceed while the original check finishes. Integration rechecks the input versions; only the joined product can earn release qualification. Don't replay the outstanding goal, and don't launch a second audit of the same comparison.

The scout and its evidence follow-ups receive the **selected blob's immutable UTF-8 text** as reference context. When it does not fit, request `needs-evidence` with the displayed `detail` and an optional literal `match`. Binary references are marked unavailable to the scout. Neither the blob nor its filename is a committed product citation. Follow-ups show `iterationFrom` in owner status.

If an ordinary assignment or scoped comparison contains a clause that contradicts the frozen product, the owner can request `foundry_correct({run,grain,review,worker,clause,file,excerpt})` **before the original bound writer submits**. Use the node's assigning review (not `iterationFrom`), a literal substring including its whitespace, and a verbatim excerpt at `review.base:file`. Inspect both task versions in the approval dialog. Approve only removal of the contradiction, not a new product decision. Foundry preserves the original report, worktree, token and checks. It does not wake a still-bound writer: direct that writer to read its updated task in `foundry_status`. For an ordinary assignment the citation is for the owner only; it grants the writer no additional reads.

For a single-directory **ordinary assignment already stopped via `missingInput`** before submission, add `preview` with the exact preserved preview commit to the same request. The product goal must be settled and unmet or unavailable, the reviewed directory and evidence unchanged, and one repair and assignment slot available. Approval keeps the original stop, preview and task in `reviews[].correction.resumed.prior`; it delivers the corrected task to the **same writer in the same worktree** under a new token. The old token cannot submit. A preview or repair notice does not integrate anything: the writer must still submit and pass the normal checks. A stale request, missing preview or declined approval cannot reopen the assignment.

While writing, `foundry_preview({run,token})` pins only the assigned directory on its frozen generation and returns the latest draft commit in the node's `preview` field. The owner can build that commit in a disposable export and compare one affected scene, then send feedback to the same writer. Unchanged bytes give the same commit. Don't repeat the comparison without a changed draft, target or observation. A preview doesn't build the app, run evaluators, reserve work, or count as a checkpoint. Submit when ready; release still requires passing both checks on the exact joined product.

Queuing a note does not wake discovery or change an existing review. Research workflows and manual rereviews do not consume it. Owner status lists distinct pending notes in `pendingReviewNotes`. Once attached, `reviews[].note` identifies the first and `otherNotes` lists any others. Attachment does not prove the scout acted on a note. An identical request is idempotent.

| Tool | Who uses it | Result |
|---|---|---|
| `foundry_start({source})` | Operator's session, on explicit request | Activate the committed brief. A seed names the requested grains; otherwise start charter review. |
| `foundry_resume({source})` | Owning session, on explicit request | Continue a paused run or retry a recoverable stall without pausing. Never create a run. |
| `foundry_publish({run,file,to,token?})` | Owner, or bound writer publishing from its own directory | Snapshot one selected regular file, including untracked images, for writers in the named output directories or charter areas. Does not change any worktree or restart submitted work. |
| `foundry_submit({run,token})` | Bound writer, from its worktree | Capture all assigned directories and exact files together and run the committed component evaluator. |
| `foundry_status({run})` | Owner or bound participant | Read assignments, blockers and receipts. The owner also sees current questions, timing facts, checkpoint, and qualified handoff. In a goal run, `qualified` stays null until both checks pass. No side effects. |
| `foundry_pause({run})` | Owner | Stop new work. Retain worktrees, assignments, issued calls and results. |

For example, the owner can publish `file: "targets/chart.svg"` to `["screens/chart", "visual-review"]`. The notice, future kickoff and scoped status provide a command to extract the exact bytes into a temporary file from the recipient's checkout, even after the source changes. Publishing new bytes adds another version; it does not replace the old one. Delivery is not proof of use. On submit, the writer or reviewer can identify the blob IDs they used or actually compared (`usedArtifacts`, `comparedArtifacts`). Status records those reports against the submitted candidate; neither changes qualification. The repository's participants share a local Git object store: targeting controls delivery, not OS-level access. Do not publish secrets.

**Tool permissions:** An explicit start or resume from the owner authorizes the named committed brief without a second Foundry dialog. Autopilot controls how the session works, not what it may execute. Before activation, Foundry reads the owner's managed settings and selected tool permission mode. If settings are unresolved, unreadable, or set to Manual, it reports the blocker without running a baseline or starting workers. Use Assisted if your policy allows it; Allow All is not required. Foundry never changes settings or approves a tool call. A ready owner does not guarantee prompt-free tools, hook registration, or permissions in a child.

In **Interactive Assisted**, Foundry asks about decisions such as giving a new writer an old candidate, transferring files, classifying historical inputs as test-only, or changing an evaluator. It does not ask again to carry out work already authorized on verified inputs. **Autopilot** and **Approve all tool calls** omit eligible yes/no forms when host policy permits. Mixed target adoption still requires an explicit operator confirmation. Neither mode answers a product question such as which currency to display; unrelated work can continue while that question is open.

### Regeneration and checks

- Writers normally start at a parentless commit omitting the assigned directory. An approved narrow successor or ownership restoration starts with the current checked directory instead; only `foundry_grant` (reuse) seeds it from a failed candidate. Its specification, interface and required outputs are present. If its directory already exists at the selected revision, status records `{directory, revision, tree}` as `priorSource`. Consult it only when the specification permits it. It is metadata, not an operator-approved `baseline`. An explicit pin changes neither the product merge base nor the evaluator. This generation context is not an OS sandbox against reading repository history.
- **Within one assignment**, the writer starts native `task` agents in parallel for independent pieces: for example, one implements an encoder and another a decoder, while the writer owns the shared exports. Helpers share the worktree and input restrictions, not the submit token. The writer collects the results, reviews and integrates the files, and submits once. Small changes and bounded repairs can stay solo. There is no second scheduler, desktop session, or Foundry approval. Submission checks the native task list before capture. A running agent blocks unless its task and launch IDs match a direct agent of a bound Foundry discovery workflow hosted by that writer. The refusal names the remaining task IDs. Failed lookups leave the same attempt writable; idle agents and unrelated shells don't hold it up. Helper reports are never evaluator receipts.
- Component evaluators receive `FOUNDRY_GRAIN` and `FOUNDRY_DIRECTORIES` (a JSON array of all roots, in canonical order). `FOUNDRY_DIRECTORY` is set only for a single root. `FOUNDRY_OUTPUTS` maps each output ID in the milestone candidate to its directory string or array. Use multi-root assignments only with checks that understand this shape. Prior source metadata and approved inventories likewise list the existing per-directory pins for a multi-root assignment; no common ancestor is granted.
- Product evaluators also receive `FOUNDRY_OWNERSHIP`, a JSON map from each real grain ID to `{directories,files}`. For a mixed grant the compatibility `FOUNDRY_OUTPUTS` value is its primary directory **only**. Match files by equality and directories by equality or a slash-delimited descendant; a unique owner can be named with `FOUNDRY_REPAIR=<grainId>`. Do not attribute unrelated or ambiguous paths.
- In an opted-in version-2 area brief (`"ownership":"exact-files"`), the owner may add `files:[...]` to a source-backed comparison on a settled exit-2 checkpoint. The listed files must already be regular files and cannot overlap another grant or conserved path. Approval names the primary directory and exact files separately. The scout must propose that same `{primary,files}` grant; the component sees the primary as `FOUNDRY_DIRECTORY` and the files as JSON in `FOUNDRY_FILES`. Capture never widens a file to its parent. Existing briefs require a separately approved product evaluator upgrade before their first mixed grant.
- **Retain except transferred:** an explicitly capable checker subtracts `exclude:{directories,files}` from each positive ownership entry using the same path rules. For example, the owner of `pkg` may exclude directory `pkg/picker` and exact file `pkg/views/index`. Only the receiver matches those paths; `pkg/picker-new`, `pkg/views/menu` and future siblings remain with the parent. `FOUNDRY_OUTPUTS` is unchanged and cannot establish unique ownership. The exact map is frozen on the product reservation and exported in qualification v4. [Owner rollout and transfer preflight](../../skills/foundry/references/runs.md#status) require distinct checker and transfer approvals on existing exact-file runs.
- In a goal run, Foundry checks published outputs on top of the last checkpoint without waiting for unrelated writers. Their drafts stay out; their assignments and input pins stay intact. A published directory remains owned until its product check passes. A fresh review can then propose a successor, subject to the existing consumer pins. A passing intermediate goal cannot close an admitted writer, and an issued product check is never replayed to include later work.
- A signed `writer-relinquished` or `writer-cannot-repair` stop can support one separately approved, strictly narrower successor on the current checked product. The stopped grant stays reserved outside the named paths. The new writer starts from current bytes, not the failed candidate, under the original component evaluator. See the [owner procedure](../../skills/foundry/references/runs.md#status). Ordinary repartition cannot retire part of a checked mixed grant. If an older reader already issued a conflicting writer, its evidence remains available but the conflicting product is held, not qualified.
- `foundry_grant` (restore) can resolve a specific older-reader displacement **forward**: one existing owner keeps every exact file and a fresh writer checks only the unchanged, orphaned primary. A separate approval names both owners, the historical and current product checks, and the current goal. A published retaining writer's scout citation alone is not a dependency if the same file was delivered and is unchanged on the checkpoint; actual writer inputs and other consumers still block restoration. The next product records the new ownership map under a distinct commit even if no bytes changed. Its new goal can still fail. This never restores an old file version, rewrites a receipt, or rechecks an already-passing component.
- `foundry_check` (pair) is a read-only follow-up if that unchanged primary received a signed exit 1 on the checkpoint, but the published retaining owner has different integration bytes. The explicit request binds the failed component, current checkpoint and goal, and the exact retaining candidate and passing component. Foundry verifies those pins and runs the original evaluator once on the new assembly, without creating a writer or opening another dialog. Proof keeps both outcomes. Only a passing pair can proceed to a fresh joined product and goal; a negative pair stops.
- If a negative pair exposes an ambiguous observer inside the primary, `foundry_grant` (observer) can staff one **new Foundry writer**, on the failed assembly, for one named existing observer file and original blob. It does not accept an owner-authored patch. The writer previews a one-file change and demonstrates intact and fault controls; the operator reviews the unchanged assertions and approves the exact preview before that writer submits. Neither earlier failure is overridden. A new failure stops; a pass still needs a fresh joined product and goal.
- After the **final** diagnostic fails, release is still held, but the run owner can request `foundry_grant` (production) on operator direction. Select the actual producer (the restored primary or its published retaining owner) and name the exact source and repository test files. A fresh grant starts on the failed assembly; it is not permission to edit the observer or conserved evaluators. If the regression cannot be reproduced, the writer reports `missingInput` and the original ownership and evidence remain. A changed submission runs both existing component evaluators on the **same** commit. Only two passes can enter normal integration. A negative result keeps both original assignments intact and records the new receipts in proof status; the same failed assembly cannot be submitted again.
- If that diagnostic component itself failed and still conflates observation phases, a separate `foundry_grant` (observer) request with `previous:{check,candidate,phases}` can authorize one last writer on that exact failed candidate, same observer file and unchanged retainer. Its exact diff needs a second approval. No production edits, reverting to an already failed input or chain of replacements. See the replacement cases in [`work/observer.test.mjs`](work/observer.test.mjs).
- A mixed-ownership hold does not prevent an approved narrow successor in a disjoint part of the same checkpoint. The stopped grant, successor paths, cited evidence and checked prerequisites must be independent of the held owners. Only the successor's component may publish; release still needs the ownership conflict resolved and fresh joined checks. See [`work/graph.test.mjs`](work/graph.test.mjs).
- After a signed negative observer, `foundry_checkpoint` can request **one non-release checkpoint** for an exact independent subset of already published outputs. It starts from the last passing checkpoint, not a failed assembly. Admission requires signed pins, disjoint changes, unchanged prerequisites, and source-backed finite build-input inventories in both directions. A separate operator approval binds the entire subset and its evidence. No eligible subset means no check. The original ownership hold survives even a passing new goal; there is no handoff, cleanup, automatic retry or promotion of the held work. See the [owner procedure and evidence format](../../skills/foundry/references/runs.md#checkpoint-an-independent-subset).
- Submission captures the whole assigned directory, including ignored files and executable bits. Missing files are deletions; a missing directory removes the unit. Foundry builds the tree in a temporary Git index, leaving the writer's staging area and neighboring edits untouched. If Git ignores a reserved pathname, submission reports that path instead of silently publishing a partial directory.
- Checks run via the host's native `bash` permissions. The shell needs `node` with `node:sqlite` on `PATH` to launch the runner; the desktop Copilot binary is not a Node interpreter. `.js` and `.mjs` evaluators use that Node; other evaluators must be executable. Raw Git blobs are streamed into a temporary directory, without smudge filters, export substitutions or the writer's uncommitted files. Use externally installed dependencies or temp space outside the product. End with the product unchanged. Symlinks, submodules, special files and case-aliased paths are unsupported. As with other local builds, run only trusted repository code.
- A component failure returns its bounded repair to the responsible writer. A failed product evaluator can print exactly one `FOUNDRY_REPAIR=<grain-id>` line to stdout to identify responsibility. Changing a shared output regenerates consumers pinned to its superseded version, but preserves past qualified commits and their receipts. An unattributed product failure keeps the checked components and reports a blocker. If a later observation adds a missing grain, the next candidate includes those components without staffing them again. A native refusal or infrastructure error is not a failed implementation.
- A bound writer that cannot generate its complete output from permitted inputs may end its writable attempt with `foundry_submit({run,token,missingInput:"..."})`. No candidate or component receipt is created; local files and prior checkpoints are untouched. In discovery, independent published outputs can now be checked against the complete preceding checkpoint while consumers of the blocked assignment still wait. A seeded one-off still needs all of its requested outputs. The report grants no reads, earns no pass and does not restart the writer.
- When the writer receives an inline repair for a verified exit-2 component but cannot proceed under its assignment, its status shows `cannotRepair.check`. `foundry_submit({run,token,cannotRepair:{check,reason}})` releases that repair without capturing edits or repeating the check. A missing-input report on that same repair also preserves the checked candidate. Both the exact runner diagnostic and the writer's limitation reach the next charter review. A single new, distinct task for the same directory and check may explicitly `replace:[oldId]` when the packet contains that stop; a linked blocker or scoped comparison may also support the handoff. Pending calls, consumers, unqualified inputs and stale review pins still hold ownership. The predecessor's candidate and preview remain history, not successor inputs or qualification.
- A different stop, `foundry_submit({run,token,relinquish:{check,reason}})`, is for an original writer with no genuine scoped fix and no missing input. Its own `writing` node must show `relinquish.check`: the last signed nonzero component verdict and its exact inline repair token or confirmed repair delivery must match. An eligible inline exit 2 still uses `cannotRepair`. A relinquished repair becomes `blocked`, retaining its verdict, checked commit and any preview without submitting new bytes or starting another check. This is not an owner override, an assignment refund, a handoff or a product pass.
- In an active goal run, `foundry_grant({run,inspectBaseline:{grains:["assignment-id"]}})` asks the operator to let an original missing-input writer inspect only regular files in its unchanged, pinned inventory. The operator sees the recipient, charter, directory, revision and tree. Approve an omitted permission, never an explicit prohibition. This can happen during a goal check: the original writer reads its own `foundry_status` for `readGrant`. The grant sends no notice, checks out no files, starts no work and spends no repair. The owner can tell the writer to check status.
- To **resume work**, the owner separately uses `foundry_grant({run,repairBaseline:{grains:["assignment-id"]}})` after a settled, unmet goal. This can also be used without prior inspection. It rechecks the assignment, current prerequisites, unchanged inventory and budget, and asks for approval to start one bounded repair per writer. Inspection alone cannot authorize a submission. Both forms are all-or-nothing and neither changes the charter or grants access to other paths or revisions.
- If the writer stopped before a reference notice was issued, that reservation is not delivery and does not block baseline approval. An issued notice with no confirmed reply still blocks recovery; it is never replayed.
- If the evaluator completed but the runner verified that the exported tree changed, the component receipt records `exit: null, failure: "changed-export"`. It cannot pass, even if the evaluator exited zero. The same writer gets the usual bounded repair; putting verifier-like text in evaluator output cannot produce this verdict.
- The product check freezes the **combined** outputs on the current target tip. If new work is admitted or the target moves during evaluation, the old result cannot qualify the new candidate. Nonoverlapping target edits are incorporated and rechecked; incompatible edits to an owned directory block rather than disappear. Inspect the final changes with `git diff <target-tip> <qualified>`. A generated candidate has the evaluated target tip as its parent; if the baseline already passed, `qualified` is the tip itself. Foundry does not land it.
- Every seeded output is required. In discovery, if a grain is blocked, independent outputs can still qualify **if the product evaluator passes**. Its blocked grain and dependents remain visible and are not marked complete.

### Hand off and measure the result

**Shared failed steps.** A goal evaluator that actually observed one failed step can write one stdout line, for example `FOUNDRY_BLOCKERS=[{"id":"open-item","directory":"desk/items","blocked":49}]`, and exit 1. `blocked` counts distinct dependent journeys **not run**, excluding the failed journey. Use stable step IDs, unique per receipt, and the responsible production directory. On a later product, report `{"id":"open-item","directory":"desk/items","passed":true}` in that list only if the step itself was observed to pass. A missing marker, component pass, writer report or owner attribution never verifies a step; a step pass never qualifies the product. Stderr, incomplete evaluations and conflicting records cannot supply these hints.

A goal that exits 2 can report a pass-only blocker list while release evidence is missing. For historical scheduling only, Foundry also recognizes an owner's verbatim, uniquely labelled `step: gap - reason` (or `step: gap — reason`) receipt line followed by an unambiguous `step: passed` line on the same target and evaluator pin. That stops new work based solely on the answered step, including follow-ups from an already issued scout; it does not mark a legacy blocker verified. Omission, an empty feedback list, a similarly named step or a generic baseline success cannot stand in for that observation. Outstanding calls and independently grounded investigations keep their original scope.

Foundry gives undelivered blocker evidence priority by the number of affected journeys. With a worker cap, ties go to the least recently reviewed squad, including squads not yet reviewed. Once the responsible squad receives the evidence, that blocker no longer gives it priority. A scout explicitly links a proposed repair (`addresses:[{id,grain}]`) or an already bound assignment (`{id,grain,worker}`). Sharing its directory does not make an unrelated writer responsible. If the review leaves the step without an owner, Foundry reserves one coordinator notice per receipt and step, visible alongside the ownership state in `foundry_status().sharedBlockers`. Other squads can still work. A delivered blocker linked to one fresh exact-directory repair can support the same guarded sequential handoff as an owner-scoped comparison.

For an existing run whose current unmet goal receipt lacks the marker, the owner can call `foundry_attribute({run,receipt,id,directory,blocked,excerpt})` with a verbatim diagnostic and a separately established count. This records **owner attribution**, not new evaluator evidence. It can wake discovery on an unchanged stalled checkpoint; it neither replays the goal nor overwrites a receipt. If the observation or count is unknown, do not invent it.

Qualification reserves a notice to the owner in the same ledger transition that records the checked product. Use `handoff.commit` and `handoff.target` to inspect **exactly** what passed: `git diff <checked-target> <qualified>`. The branch is not updated. A notice may still await native delivery; the qualified result remains readable from status. For a portable record use `foundry_status({run, detail:"proof"})` in the owner. The [handoff guide](../../skills/foundry/references/handoff.md#export-a-goal-record-on-request) explains how to transfer the retained objects and replay trusted checks in another clone; a SHA alone is not delivery.

Keep writer sessions after handoff. Only if the operator separately requests cleanup, follow the [owner handoff guide](../../skills/foundry/references/handoff.md) for the named writer, including a fresh check immediately before the action. Unknown, unique, or ongoing work means **keep the session**.

[`/foundry measure <run-id>`](../../skills/foundry/references/metrics.md) reports wall time from activation to the first writer's verified kickoff in native history and to exact product qualification. It distinguishes kickoff from Foundry's confirmation of a writer binding, which can arrive later after recovery. Missing history is unknown. A reservation is not a writer; a checkpoint is not a finished goal. A successful baseline may need no writer. Count only observed writer usage attributable to this run, not lifetime totals or estimates for the owner, helpers or workflows.

### Interruptions

Foundry reconciles until no already-authorized action is available. The owner and issuers with unfinished work observe the ledger and target ref even without a chat turn. A changed or restored ref is reassessed, not adopted. The original issuer also watches held permissions, including a continuation that becomes permitted after reconnect. Status and the board are read-only. A closed session cannot run an observer; reopen its original issuer, not a replacement run.

If the ledger is temporarily locked when the session opens, the issuer retries its registration scan with backoff until it can attach to its existing obligations. Corruption or an incompatible reader is reported, not polled. After upgrading an issuer already stuck without observers, reload Foundry **in that issuer's session**. It finds the original ledger; there is no need to restart or resume the factory.

A lock after registration does not consume a scheduler wake or a confirmed capacity retry. The issuer rechecks the same ledger, even when its checksum stays unchanged. A transient failure reading execution mode is not permission to dispatch and does not disable future observations. A slow permission sample does not block independent reads of an original call's history.

If an owner has answered but the ledger is busy, the live issuer retries **recording** that reply, not presenting the question. A superseding presentation wins. If the issuer already closed and the answer was never saved, only explicit recovery of the original question can collect it again.

Open **State explorer** on the work graph, or open `foundry-board` with `{machine:true}` without a run. The chart begins in its initial configuration. Click a state to read what it represents. Select an event name in **State** to read its purpose without firing it. Expand **Ordered rules** for each branch's purpose, guards, destination, action, admission and diagnostic when present. A highlighted arrow sends the event; an inactive arrow inspects it. **Set as test state** lets you try a projected state with no incoming arrow. The issuer's parallel regions share one event.

Follow the straight runs and rounded elbows between states. Where several lanes enter the same state, the inner one turns sooner and more tightly; the outer one continues closer before it turns. Follow either line to its own arrowhead. Hover or focus a bordered event label to pick out its line without sending the event, even when inactive. An explicit loop stays next to its own box, while a targetless action stays **inside** it. A state's position is not its priority. **Events** rewinds state and guard inputs; **Definition** shows the installed declaration. The work graph uses soft dependency curves instead. Both layouts are first-party and work offline.

#### Permissions and checkpoint progress

Before issuing new work, including a `prepared` call, Foundry checks the **issuing session's** permissions. If managed settings are resolved and that session has selected **Manual**, only its unissued calls are held. `foundry_status.pending` shows the reason and issuer; other authorized sessions continue. After selecting a permitted mode in the held session, its next turn rechecks the original reservation. No owner restart or replacement worker is needed.

If managed policy is unresolved, restricts the selected mode, or cannot be read, Foundry pauses the run and records which issuer and reservation caused it. Only that issuer can automatically clear this exact hold after its live policy permits work. `foundry_status({run,detail:"permissions"})` in that session is diagnostic; `ready:true` does not itself change anything. An operator pause during the wait cancels automatic recovery. A pause from an older reader with no structured cause remains manual: an operator could have paused again while the old diagnostic was still displayed.

A passing product checkpoint can support discovery while its goal is still running or after it exits 2. On the same target, Foundry looks back across consecutive missing observations to the last exit-1 diagnostic. If it named a squad or blocker directory, its owners get the first scout slots, not all the slots. Another charter can inspect its own unresolved product evidence or finish a survey previously blocked before packet delivery. A settled no-gap charter is not reopened just because another area failed. An unstructured diagnostic can prompt a broader charter survey only after exit 2; no prior failure means no automatic survey.

`reviews[].lead` names the checkpoint, the historical `receipt`, and either the issued `pending` goal or the completed `missing` receipt. An independent investigation also names its `priorReview`. None is a new verdict: an independent proposal must cite delivered files in its own area. Disjoint writers may bind on verified inputs without waiting for the blocker scout. No unchanged release check is retried, and a pending goal that later passes cannot qualify changed bytes.

To retry release verification itself, supply the missing observation and use `/foundry resume <plan>` in the owner session. No pause is needed. This reserves a fresh check of the retained candidate, keeping the previous receipt. A moved target must be incorporated and checked before it can qualify; a denied or uncertain call is not an exit-2 receipt.

Integrating already-admitted work is not a retry. On a settled exit 2 with an exact passing checkpoint on the current target, normal scheduling considers all published components, including a lone output from an ordinary review. The join validates ownership, frozen citations and dependency pins against the assembled tree. Changed bytes require an ordinary product pass before a fresh goal check; an unchanged tree is marked repeated without retrying the old goal. This does not admit ordinary new assignments, grant ownership, or approve a product-checker change.

#### Writer and scout dispatch

Foundry records reservations before issuing native calls. Only an explicitly unavailable, definitely unissued native session route yields an ordinary `prepared` call. Execute it **once, unchanged, in its issuing session**. A confirmed denial blocks the assignment and releases its slot. Recovery reads backward to the start of the issuing turn: an older permission decision is not evidence for this call. Missing or conflicting receipts stay pending and never cause another creation.

For an **existing** child whose original `create_session` is `uncertain` and still unbound, use the [two-session claim](../../skills/foundry/references/runs.md#recover-an-existing-writer). Both sessions must independently prove their side from native history; a claim does not capture files or run a check. `external_tool.completed` only dismisses the request UI. It is never a launch or check receipt.

If a writer publishes and its session closes before claiming a new writer launch, an explicit owner resume can claim that same reservation. It keeps the assignment token, inputs and generation base. Only a current `ready` launch with no native call ID or permission hold can move; the owner's dispatch still checks its own permissions. An outstanding permission read in the former issuer cannot claim a launch after it moves.

Scouting requires an eligible Dynamic Workflows runtime. The issuing session schedules follow-ups; a scout workflow reports evidence without launching another workflow on its call path. When the host rejects a launch because its workflow slots are full, the same reviews stay queued. The issuer rechecks capacity automatically; no resume or extra assignment is needed. Foundry does not substitute desktop scouts if discovery is unavailable. A bound workflow can return evidence through a pause, but cannot issue work while paused. On reconnect, Foundry reads the original workflow's outcome rather than launching a second one. If a dispatch was interrupted *before* the workflow bound it, `/foundry resume <plan>` retries that read-only discovery from the owner session, even if the original issuer was a writer. This does not retry an uncertain writer creation.

A timeout, connection reset or temporary contention while reading a bound workflow's status does not mean the workflow stopped. The issuer backs off and reattaches to the same workflow while its original review is outstanding, even if nothing writes to the ledger. It does not retry the launch or overwrite the saved review on a transient read failure.

If the status already returned but could not be recorded, the issuer rechecks the same bound workflow when possible; a newer refusal takes precedence over the earlier halt. An issued workflow is never relaunched to recover a missing result.

If the native workflow reports `halted` specifically because its provider disconnected, its issuer checks that exact workflow again. On matching evidence, unchanged inputs and live permission it journals one continuation **before** calling the host. It keeps the same workflow ID, missing reports and limits; another disconnect or a lost continuation reply does not buy another automatic attempt. A generic `paused` or `halted` outcome still needs an operator. The owner can explicitly resume its own workflow; a writer-owned workflow must continue in that issuer. Never resume a cancellation, declined continuation or resource-limit failure.

A reader upgrade can instead end a bound scout with a terminal execution error before its report reaches the ledger. Reload the stale issuer so it can observe the original workflow. The [recovery procedure](../../skills/foundry/references/runs.md#pause-and-resume) handles this exact error even if already recorded: one new reservation for a still-current original review, under the normal ownership, permission and capacity checks. The old workflow is never resumed and its blocked record is retained.

`foundry_review({run,retry:{review}})` spends one available assignment on **one** still-current budget-blocked review, only on explicit owner request. Foundry verifies what happened in the completed original workflow: either the selected scout exceeded its prompt budget before using a tool, or local packet sizing failed and no agent ran. In the latter case it looks up the original goal receipt and can select a short verbatim diagnostic for that squad. Either way it checks the fresh packet against the issuing session's current budget before dispatch. Partial diagnostics cannot establish `no-gap`. The full receipt and original reviews remain in history; neither the old workflow nor its siblings are retried.

The same operation can recover a **reported source comparison** if its opening packet omitted the approved file and Foundry rejected the report for citing that exact blob. Pass the original review ID, not a new offer. Foundry verifies the saved packet, rejection and pinned product before starting one fresh scout on the same question, directory and evidence. The corrected packet must deliver the file or a citable range. The original stays blocked; `reviews[].retryOf` links the replacement to it. No new approval or writer is implied. A changed product or evaluator, superseding charter review, reserved directory, scheduling hold or exhausted capacity cannot be bypassed.

A comparison on an unmet goal or passing checkpoint can narrow its packet to the selected directory and page the index if necessary. A checkpoint comparison keeps its original direction and attached historical notes when the goal on the same product later exits 1. For a review already blocked before any scout ran, request rereview by its original review ID; do not reroute it against the goal or replay the previous workflow. If even the scout instructions and a usable evidence page cannot fit the host window, the request spends no new assignment.

A queued repair is not proof the recipient acted. A native permission or input request remains with its actual session. Pausing stops new work; an already-issued check may finish, and its result is applied on resume. A confirmed synchronous nonzero launcher exit before the runner started is not an evaluator failure. It can free a worker slot but never retries automatically. Once the runner starts, only its own receipt can settle the evaluation.

#### Check and receipt recovery

After correcting the environment, the owner may request `foundry_check({run,recover:{check}})` on explicit operator direction. Select the exact current failed component, product or goal launcher, or a **signed goal receipt with `exit:null`**. The request reserves one fresh observation without a second dialog, new writer or repair. Proof status links its pins and the original evidence in `checkRecovery`. A component uses its captured candidate on its original issuer’s next eligible turn; never resubmit the working tree. A changed product must pass its own join. A duplicate does not reserve another check; a changed target, pin or permission cannot authorize different inputs. This cannot replace a product-pin upgrade’s own verification.

For a **stopped assignment with a signed numeric component failure**, the owner can instead ask to rerun its original check against the current checked product:

```text
foundry_check({run,observe:{check, product, harness:["tests/catalog"], current:["app/catalog"]}})
foundry_check({run,repeat:{check, product, after:"<latest signed rerun ID>"}})
```

`check` is the original component ID; `product` is the full checked commit. Inspect the original **default invocation**, including every phase, discovered test and external helper. Declare historical test-only paths in `harness` and changed paths that must stay at the checked product in `current` (including unrelated changes). Unchanged paths need no declaration; use `harness:[]` for an entirely unchanged evaluator with no changed test inputs. An absent, test-only assignment directory can be restored whole. For a changed existing directory, name exact test files; never restore mixed production and tests together. Every difference must be accounted for. If a dependency's role is unknown, report the specific path and do not approve. The runner verifies the disposable export, runs the original evaluator with its assignment environment, and signs the product and the historical harness identity. No working tree, assignment, repair budget or release verdict is changed.

The board shows the latest observation and expandable **Previous attempts**. Full receipts and their links are in proof status under `checkRecovery`. An identical request is idempotent. For an intentional repeat on the same product, pass the latest signed rerun ID as `after`. Foundry verifies the signed, unchanged input partition instead of asking to classify it again. A pending, refused or unconfirmed launch is not a signed observation.

On the owner board, **Passed on build · not integrated** means the latest signed rerun for this exact stopped check passed on the displayed checkpoint. Dependents still wait. For a batch of entirely absent, disjoint **test-only** directories, `foundry_deliver({run,checkpoint,goal,reruns})` requests approval to integrate just those directories. Use current product and goal **check IDs**, not commits, and the latest passing rerun IDs on these exact product bytes. A checker upgrade on identical bytes is allowed; a different product needs its own observations. The goal must be settled (exit 1 or 2), with no conflicting ownership, pending work or mutable assignments.

Review the listed files and subtree IDs: do not approve shipped code, mixed directories, external historical overlays or unknown inputs. Foundry keeps every existing output, runs all selected components serially on one combined commit, checks the product once, then assesses the goal afresh. A component or product failure integrates nothing. A product pass with an unmet goal integrates the tests **without qualifying a release**. Owner proof under `deliveries` links the original stops, reruns, delivery checks and goal. No target branch is changed.

A later `missingInput` stop does not invalidate an earlier signed failure. The candidate comes from that check's receipt, even if the repair cleared the node's candidate. A pre-journal runner could record `runnerStarted` and a numeric exit without a signing key. That exit stays in history but cannot authorize this route; resubmitting the writer would not authenticate it.

Numeric evaluator exits (including 137) are not interruptions. Exit 2 keeps its normal missing-evidence/resume route. If status says `claim-not-recorded` or `claimed-no-outcome`, wait for the original native evidence; absence, elapsed time or a shell exit after claim does not authorize replacement. A permanently lost signing runner has no same-run generic recovery.

New runners write the original receipt once to `work.sqlite.outcomes`, next to the ledger, without decoding the run again after evaluation. A current reader verifies the run, reservation, native call, commit and evaluator pin before applying it. Back up both databases together. A shell exit, feedback file or runner-start marker is not a substitute: if a runner stopped before writing its receipt (including one from before this change), the result remains unknown and is not replayed.

`foundry_retire({run,check})` is an owner-approved recovery for one pre-journal goal runner that terminated with a snapshot decoder failure. It requires the original owner's matching native shell notification and diagnostic, the unchanged checked checkpoint and pin, and published outputs ready to integrate. It records the native event IDs in `goalChecks[].infrastructureFailure`, leaves the old receipt absent, and uses normal product and goal checks for the new tree. Repeating the request does not launch additional work.

Older component receipts did not distinguish an export-verifier exception from other incomplete evaluations. Neither reload nor owner resume reclassifies them. When the original writer's status has `changedFrom`, the writer may submit a **different** complete directory from its original worktree with `foundry_submit({run, token, changedFrom})`, copying both fields from status. This spends one authorized repair and one assignment, and reserves a fresh exclusive check; the old receipt stays unchanged. The run must be active, permissions ready, inputs still current, and a worker slot available. No such option is offered for a refusal, missing runner receipt or newly recorded process interruption.

For an exhausted **exit-1 component**, `foundry_grant({run,reuse:{grain,check,candidate,blob}})` requests one operator-approved successor in the same goal run. `check` is the node's component reservation ID, `candidate` its receipt commit, and `blob` a correction already offered to that directory. The new writer starts with exactly the retained directory on the current checked product, under the same task (including approved corrections), grain ID, prerequisites and component evaluator. A later disjoint checkpoint is fine; changed reviewed inputs, a repin, an outstanding join, or missing capacity prevent admission. The new writer consumes one assignment, not a reset of the repair allowance. An unchanged submission is refused before checking. Node `reuse` identifies the predecessor and the new reservation. Neither the reference nor the old receipt counts as a pass.

Foundry processes parallel replies independently, including after reload. A slow history lookup does not hold up an unissued assignment or a slot freed by a confirmed refusal. The unresolved start still occupies its own slot and is never sent again. If the issuing session switches to plan mode while waiting, Foundry records the reply but starts no follow-up work there until an interactive or autopilot turn.

If a long check finishes after `submit` returns, a matching shell completion wakes the scheduler. Only the runner's recorded verdict can issue a repair. If that writer is driving the run, Foundry queues a notice in its own session to read the new token; otherwise the usual cross-session repair applies. An unconfirmed notice stays pending rather than being sent again.

Foundry retains versions and generation bases in `refs/foundry/objects/`. Linked worktrees share `foundry/work.sqlite` in the repository's common Git directory. This runtime uses ledger protocol **13**. A reported review retains its packet coverage, delivered path/blob IDs, checked versions the scout saw, and any event that reopened it. Qualification belongs to the checked product. Older ledgers are refused, not migrated or deleted. Leave an old clone intact; use a fresh clone for a new run.

`work/reader.version` identifies the session's ledger reader, independently of the SQLite protocol. Bump it when changing which records Foundry can write or interpret, including new dispatch kinds or states. An already-open session with a different installed reader refuses ledger access and asks for a local extension reload. Reload that session, then check the existing run; don't recreate it. A matching reader still checks the ledger and reports invalid snapshots as errors.

#### Changing an evaluator or target

The owner can [repin the final goal evaluator](../../skills/foundry/references/runs.md#evaluator-repinning) to an approved, committed harness fix without changing the contract base or the target. Keep the fix on a separate ref. Issued checks finish against their reserved evaluator; the updated goal is checked on the product itself, with only the approved evaluator delta overlaid in its temporary export. Product and component checks do not use the overlay.

If a combined candidate failed its product check, repinning rechecks the last assessed baseline or passing checkpoint, not the failed candidate. Its product check is not retried. If the new goal receipt still shows a gap, fresh scouts may add missing work; a report prepared under the old pin cannot authorize it.

An explicitly selected `foundry_repin` **`kind:"product"`** instead upgrades the product checker and opts this run into exact-file comparisons. It requires its own reviewed commit, operator consent, settled goal and quiescent checked checkpoint. The immutable `productRepins` lineage binds the prior checkpoint and goal to one new product reservation on those same bytes and output pins. Only a passing new product check permits a fresh goal; goal, component and product overlays are never interchanged. See the [operator procedure, including bound-writer restrictions](../../skills/foundry/references/runs.md#evaluator-repinning).

**`kind:"target"`** adopts reviewed changes to the charter and acceptance rules together on a descendant target. It keeps the activated plan, ownership mode, original assignments and receipts. The owner names the release change and the union of the conserved diffs against the current contract **and both approved evaluator pins**. The operator must confirm this change even in Autopilot. All included components run on separate exports of the joined commit, then the product and goal must pass on that commit. An old pass cannot qualify it; its target branch is never moved. See [mixed target adoption](../../skills/foundry/references/runs.md#mixed-target-adoption).

A writer's first signed exit 2 can leave a repair queued but never granted. Target adoption distinguishes this from writable work: it names eligible, unconsumed candidates in the approval and retains them outside the new product. It does not retry the observation, delete a pre-existing directory, or mark the candidate successful. Actual grants, checks, dependencies and ownership conflicts still hold adoption.

For a conflicting **unowned** text file, target adoption can apply one reviewed, reversible replacement to the checkpoint in a temporary index. `resolutions` lists every conflict's exact path, common regular-file mode and four blob IDs. The approval shows the old and new text; the signed product observation binds the manifest to the checked assembly. This is not a general content merge, a change to an included output, or authority to resume a paused run.

A scout for the old pin keeps its slot while its native attempt is running or unconfirmed. Once the attempt is confirmed paused or halted, Foundry retires that review instead of resuming it, and the new pin can use the slot. The original assignment still counts toward the total assignment limit.

## Development

Implementation changes must follow [Keeping the specification current](SPEC.md#keeping-the-specification-current). Run the declaration drift check as well as the behavior tests for the affected contract.

### State, signals and authority

Foundry is a dynamic graph of jobs, not one global workflow cursor. The committed brief tells squads what to discover and which evidence would count. A scout can propose different jobs after a checkpoint. Writers regenerate their own outputs from pinned inputs. A new signed result feeds discovery again until the *combined* product meets its goal, or there is no authorized next action.

| Layer | Responsibility |
|---|---|
| State-machine kernel (`work/chart.mjs`) | Immutable, serializable definitions inspired by [XState](https://stately.ai/docs/machines). A signal plus facts selects the first matching edge in a state. Selection never reads the environment or performs the named action. Invalid targets, contradictory guards and shadowed alternatives are rejected at definition time. |
| Entity machines | `assignment` consumes component receipts and queues repair; `review` admits reports; `call` distinguishes a ready reservation from an uncertain reply. `activity` keeps an operator pause separate from a policy hold. `dialog` governs an owner question; `renewal` can admit a saved report on fresh evidence without running its scout again. Release, checkpoint quiescence and workflow continuation are independent projections of the same run. |
| Work graph (`topology.mjs`, `plan.mjs`) | `needs` names producers, not execution order. Adding or replacing jobs checks new dependency paths for cycles; deleting a producer also checks surviving consumers. Unrelated jobs and their pins are not recreated. A loaded snapshot still receives full validation. Writer readiness additionally requires checked prerequisite versions and valid ownership. |
| Evidence and effects (`database.mjs`, `native.mjs`, `runner.mjs`) | The ledger owns entity states and reservations. Plan from a snapshot, compare-and-swap the result, then let the authorized issuer claim an effect. A native completion is evidence about its original call, not a component verdict. Only the exclusive runner signs a check on the pinned bytes. |
| Signal adapters (`runtime.mjs`, `supervision.mjs`, `wakes.mjs`) | Host notifications, receipt arrivals, permission changes and restored Git refs wake the relevant issuer. After reload the issuer rebuilds subscriptions from outstanding obligations. A missed notification may cause a backed-off **read**; it cannot authorize a duplicate start. |

To add a Foundry region, define `chart(id, initial, states, {description, states: stateDescriptions})`. Explain the decision the region owns, why each state exists and what each branch accomplishes. Give each edge a `description`, or use its existing human-readable `reason` once; a machine diagnostic code isn't a description. Extra data such as release admission belongs to the domain. Edges have `on`, optional `when` (boolean names, `!` for negation), and a `target` or named `action`. Bind named effects with `implement(model, handlers)`; register the executable region in `work/catalog.mjs`. The explorer does not maintain a second transition table.

`extend(model, additions, stateDescriptions)` adds states, events or guarded alternatives before the relevant fallback. It preserves unchanged purposes and accepts descriptions for new states. `compose(...models).plan(snapshot, signal, factsByRegion)` evaluates independent regions against the **same** snapshot and returns just the selected transitions. `actor(savedStates)` is an in-memory interpreter for simulations; `send` applies a signal atomically with no entry-effect replay. `install` can replace a compatible definition for future signals without resetting those actors. In a real run the ledger is the state: do not add a shadow actor or a second job queue. Distribute changes to durable semantics through the reader fence and reload the participating extensions; this does **not** mean starting a new factory or rechecking old results. No run, brief or canvas may install executable policy or expand authority at runtime.

### Goal-verdict contract for a blind rebuild

Give an independent implementation this rule, not the scheduler or its tests: return the last accepted goal commit only if the run stopped at that product and target, and its distinct product and goal evaluations both have an unambiguous runner-started, completed receipt for **that commit and the corresponding committed check**, each with exit `0`. Otherwise return no verdict. A passing baseline needs no writer. A passed milestone without final acceptance, receipts from different commits, a successful native shell reply without a runner receipt, and exit `2` are negative controls. One-off and ongoing product passes are not goal verdicts.

Compare coordinators on the same starting Git commit, fixed worker cap, and independent checks. Count false acceptances, stalls, duplicate launches, and extra operator turns before comparing time or spend. Keep the production runner and target-branch protections fixed throughout.
