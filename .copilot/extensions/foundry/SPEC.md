# Foundry regeneration specification

Foundry turns a committed product brief into a **checked Git commit**. One operator start authorizes discovery, writing and verification within that brief. A useful intermediate product is a checkpoint, not permission to declare the goal met. When evidence identifies one already-authorized next action, Foundry must take it; otherwise it must say what fact, decision, permission or budget is missing. It never lands the result on the target branch.

This is the contract for rebuilding **Foundry itself**, not a product's `.foundry/<plan>.json`, a runbook, or permission to run a factory. It specifies outcomes and interfaces, not a required source-file layout.

## What to give a new implementation

Freeze the following at one reviewed revision. If the extension directory will be regenerated wholesale, stage the inputs **outside** that directory, read-only, before removing the implementation from the disposable checkout.

The JSON is data, not a live factory or a substitute for the rules below. |
| [`work/model.d.ts`](work/model.d.ts) and [`work/reader.version`](work/reader.version) | Data-only contracts: the persisted record shapes and the current reader fence. Shape alone is insufficient: a well-formed receipt can still belong to the wrong attempt. |

These documents and declarations form one specification. The Git revision identifies its edition. Keep the old implementation and the independent checks **out of the writer's inputs** for a blind rebuild; keep the checks with the verifier. A disagreement between the specification, implementation and a test is a discrepancy to resolve, not a reason to silently choose the easiest one to pass.

## Start and authority

- **Inputs.** Resolve a named plan from committed `HEAD`, not working-tree edits. Record the activating commit, plan path and ID, existing local target ref, conserved files, squads, and evaluator pins. The target must agree with the approved contract before integration. Reject invalid paths, overlapping grants, dangling dependencies, cycles, and a goal evaluator that is also the product evaluator. A version-1 plan declares fixed grains and may select a seeded one-off; version 2 discovers work in disjoint charter areas and requires a goal. The shared-journey form pins the whole `.foundry/` tree. A referenced path is not a write grant.
- **Consent.** Preparing, reviewing or listing plans does not start one. Only the original owning session can activate or resume on operator direction; resume finds the existing ledger, never creates a replacement. Respect the issuing session's current mode, host permissions and deadline at dispatch. Autopilot is not authority to choose a product requirement, weaken an evaluator or answer a lost dialog.
- **Capacity.** A worker cap counts reserved scouts and writers, including a writer under component check or independent code review. A lifetime assignment cap separately charges each reserved scout, writer or bounded repair, not each helper or review of a submitted candidate. Refusal releases the occupied slot, not the charge. Lowering a cap drains existing work rather than cancelling it. Zero remaining assignments does not prohibit verifying already-admitted bytes.

Starting an already active or qualified run returns its state without dispatching. Starting an already paused run refuses and points to explicit resume. Neither route rewrites issued work or the activating contract.

## Machines, graph and ledger

There is no persisted global workflow cursor. A **state machine** defines how an entity or a single reconciliation pass responds to an event. Its **chart** shows those rules; it does not execute them. A dependency says **whose checked output** an assignment consumes. The ledger records **what actually happened**. A new pass starts from current evidence, not from a saved instruction pointer.

<details>
<summary>Machine declaration, evidence sources and admission modes</summary>

**The declaration executes; inspection does not.** A region has an ID, an initial state and ordered outgoing rules per state. One event and the first matching rule determine the next state value, complete next entity context, and queued effects. The rule owns its literal target, synchronous pure context reducer, and named effect. A targetless update or effect stays in the same state; an ignored event preserves the input snapshot and queues nothing. Required commands must select a rule. Guards are a conjunction of observed facts (`!` negates) or an event predicate on the rule itself. An injected fact cannot override a predicate derived from the entity and event. Reject invalid destinations, missing booleans, unbound effects and shadowed alternatives. An adapter may perform the selected effect against the original authority; it must not choose a different transition. A ledger projection writes only the resolved entity slice. No speculative plan is authorization to start a native call.

Evaluate orthogonal regions against the same pre-event snapshot. The explorer and JSON manifest project the running machines' ordered targets, guards, reducer names and effect types. They carry no executable callbacks or live capabilities. Inspection, hydration and rewind never run a reducer or deliver an effect. A compatible extension can add states and guarded alternatives without resetting an entity or replaying entry effects; removing a live state requires migration.

Each catalogued region declares its purpose and what every state represents (`info.description`, `info.states`). Each ordered alternative explains what it accomplishes (`description` or an already human-readable `reason`); an ID, action name or reason code alone is insufficient. Keep these descriptions with the executable definitions, including extensions. They survive serialization but never participate in guard selection, evidence or authority.

The board and its standalone map server must load the same executable rule definitions as the issuer without importing the planner, ledger, signer or effect executor. The host supplies the live board with already-scoped facts. A historical reader must carry its own rule modules rather than using the current edition's.

The transition lists in `spec/interface.json` are normative, including their order. The important distinction between their inputs is **where the evidence comes from**:

| Region | Source of truth and limit of the decision |
|---|---|
| `activity` | Run activation, explicit pause, and the issuer/effect/token of a managed hold. Only that current hold can clear on a permission signal. |
| `reconciliation`, `scheduling` | One issuer wake and one planning pass, respectively. Their phases are transient, not additional durable run states. Reconciliation checks live authority and handles history/dispatch in independent lanes. Scheduling orders review settlement, release assessment, writer allocation, joins and discovery on a private ledger snapshot. Only committing a revalidated plan, then claiming the exact reservation, permits an external call. |
| `assignment`, `review`, `call` | A grain's bound grant, a charter's one journaled report, and an issuer's one external reservation are different entities. `waiting` is not writable; `reported` is not admitted; `issued` or `uncertain` is not `ready`. A component outcome applies only to the current pinned attempt. |
| `inspection` | Independent review belongs to the writing assignment, not a separate factory stage or a new writer. The assignment owns the frozen candidate and decides whether to publish or repair. The inspection machine owns the review request, workflow binding and eligible recovery. A fixed grain includes its exact conserved specification as read-only task context. Only the matching issuer, dispatch ticket, component and workflow can settle the review; a scout report or signed component pass cannot approve it. |
| `correction-author` | One bounded author owns one disjoint part of a draft. Journal its dispatch before calling the native workflow; expose the frozen packet only to its binding. An uncertain reply retains the claim; only confirmed pre-admission capacity refusal can requeue it. Returning a verified manifest does not approve or publish the bytes. |
| `release-preflight`, `release`, `quiescence` | Check deadline, target, conserved inputs and ownership before applying the ordinary goal decision. The exact checkpoint and outstanding work determine admission; permitting scoped work or a join is not permission to release. During target adoption an unissued, unconsumed, ordinary first exit-2 repair can be retained as history; an outstanding grant or check cannot be retired on that evidence. |
| `dialog`, `renewal`, `workflow` | The original presentation, saved report or native workflow ID matters. A reply must match its presentation. If the dialog host throws before returning a promise or rejects it later, record that presentation as unavailable; only explicit recovery may open it again. Renew a report only on revalidated inputs. Continue a verified provider disconnect at most once under the automatic claim; a generic halt is not that signal. |
| `supervision` and `history` (parallel) | The issuer observes policy, target, ledger and its outstanding calls independently. A clock tick requests a read, not a verdict. A slow native lookup must not serialize unrelated work. |

For release, `moved` compares the assessed target with the observed tip; `exactProduct` requires the current checked product, target, commit and product-evaluator receipt, not just equal tree contents. `review` and `work` concern eligible outstanding obligations, not every historical card. Derive these facts from the ledger and verified Git inputs, never from a timer or an agent's assertion. Interpret admission separately from the selected action: `open` permits normal discovery, writers and integration; `checkpoint` permits scoped work but no join; `repaired-checkpoint` also permits a **changed** join; `join-only` does not staff new work. The two ownership-repair modes permit only the designated repairs, not discovery or a join. `closed` permits none of those effects.

</details>

<details>
<summary>Dynamic dependency edits and checked inputs</summary>

A grain has an ID, a task or specification, an ownership scope, a component check and `needs` naming actual producer outputs. An area review may add, split, replace or retire work atomically. Reject the entire edit if it would introduce overlap, a cycle, an absent producer or an invalid ownership transfer. If an issued consumer still needs a version, defer the change rather than withdrawing the consumer. Readiness requires checked versions of the direct and transitive inputs, not just an acyclic graph. Preserve unrelated nodes and their receipts; a changed checkpoint is not itself a reason to restart every writer. At admission and integration revalidate the exact scope, prerequisite pins and cited evidence.

An absent producer rejects the edit, not the saved report. When other reports declare all its external producers, the owner revalidates the latest bound report on its original evidence and target and runs normal admission again. Drain newly released reports before staffing. Never infer a producer, silently edit an issued job, or use mutually missing names to admit a cycle. Adding a direct edge to an already pinned ancestor changes the graph declaration, not the identity of previously failed work on those same inputs.

With a finite assignment budget, leave room for admitted waiters before commissioning speculative discovery during ordinary work or a pending goal on the current target. Count each waiter once, regardless of the number of paths to it. An idle or blocked ancestor does not reserve budget for its descendants. This priority is not a new charge or a refund: an already consumed assignment stays consumed.

</details>

<details>
<summary>Persistence, transaction boundaries and exact effect identity</summary>

**Persistence and effects.** Store the run in the common Git directory shared by its worktrees, not a session's process memory. Protocol 13 uses `foundry/work.sqlite`: `runs(id,owner,document,checksum)` keyed by run ID, with a SHA-256 hex checksum of the UTF-8 JSON document. The separate `work.sqlite.outcomes` journal (version 1) stores `(run,effect,signature,document)` with a unique `(run,effect)` key. Validate identity, checksum, record shape, graph and evidence lineage on read; refuse an incompatible or corrupt store without resetting it. A stale extension reader must reload, not rewrite someone else's ledger.

Plan graph changes from a snapshot outside the write lock; commit them only if the snapshot and relevant external pins still match. Make bounded claims atomically. Never await host I/O in a ledger transaction. Persist a reservation before issuing its external effect. Reconcile a reply to its exact issuer, call ID, operation and arguments. Duplicate observations of the same completion are idempotent; contradictory identities remain unresolved. Retain referenced Git objects independently of the user's branch at `refs/foundry/objects/<oid>`.

The SQL protocol is not the document format. Read either the historical untagged root `nodes` or `format:"foundry-run/2"` with `graph.nodes` and **no** root `nodes`; never read a mixture. Both keep `policy.source`, `effects[].nativeId` and the SQL owner discoverable. Reads and aborted or no-op plans never convert. The first committed edit crosses the fence atomically, without translating historical signatures. New documents declare `reviewContract:"required"|"legacy-no-review"` independently of the inspection list. Only a validated historical document can carry the latter contract forward; creating a run requires the former. Omission or contradiction is not consent to bypass review.

Reuse only immutable decoded facts for the validated document and observed spool revision; planners and claims receive private drafts. An unchanged scheduling decision must not re-encode old diagnostic bodies just to compare its draft. Detect an externally created journal, a bad checksum and altered existing rows. A malformed, unsupported, missing required or mismatched original outcome is a named integrity hold, not a verdict. Preserve the original row and block any publication or release that depends on it; independently validated work may continue. A corrupt run, graph or ownership lineage is not a per-attempt hold. A warm read can avoid parsing; a cold validation of a whole document necessarily reads history.

</details>

## From brief to checked product

1. **Assess the baseline.** Run the goal on the pinned target. A goal pass still needs a distinct product pass on the same bytes; an already-good baseline needs no writer. On an observed gap, send the committed journey, charter, diagnostic and relevant pinned inputs to tool-less scouts. One slow squad does not block the others.
2. **Discover and admit.** A scout returns one structured observation with a reason and citations. `regenerate` proposes scoped work; the non-writing outcomes carry no grains. A partial packet can support a specific finding, not exhaustive `no-gap`. A listed filename is not a delivered citation. Evidence requests advance a pinned cursor or literal search; no-progress reads do not loop. Opted-in researchers can supply cited findings and remaining unknowns, not assignments, access grants or verdicts. Only a genuine product choice or external action goes to the operator.
   An unmet goal's old stall closes staffing and integration, not discovery of newly attributed failures. The ordinary review selector decides whether an unused failure or in-scope page can reach a charter, including one waiting for an unrelated input. Status and unowned notices use that same selector, current charter version, and remaining budget after protecting admitted writers. A busy slot can delay a review; a spent offer or a different comparison directory cannot promise one. Do not name a review that never received the finding. Recheck before sending a notice; a new packet neither supplies the missing input nor authorizes research or a writer.
3. **Bind and regenerate.** The original issuer binds a confirmed worker identity and token to one generation in its native worktree. Normally the generation is parentless and omits the assigned directories. Existing exact integration files are a separate grant; neither parent nor siblings are implied. A prior tree is metadata unless the charter or a specific approval permits the read. A pooled writer receives a fresh checkout, not a recycled draft. Helpers may work within the writer's scope but never receive its token or submit. A preview pins a draft only; previewing unchanged bytes on the same generation must return the same commit.
4. **Submit, check, review and join.** Only the bound writer submits, after joining helpers. Capture all granted roots and exact files together; a missing input stops the attempt without capturing partial bytes. A signed component pass freezes the candidate for independent Rubber Duck review. Only approval publishes it to dependent writers or the product join. Blocking findings return to the same writer if its grant and repair budget allow; changed bytes need a fresh component pass and review. An unavailable or ambiguous review is not approval. Assemble only compatible, published outputs over the checkpoint/target. Preserve unrelated target changes and the user's real index and worktree. A newly admitted output may require another join, never replay of an issued product check.

   **Resume on supplied input.** If an ordinary bound writer stops before submission and names the exact missing reference blob, a subsequent owner offer to its output or an authenticated direct response from its producing writer can settle the match. The consumer may also specify the producer assignment and path; only that original grant and version can answer. Bind a producer response to its writer, source, exact blob, intended output and stopped attempt. Read a checked dependency from its exact approved candidate with its signed component, never a working copy. An independent working-copy blob is a read-only reference, not a dependency, candidate or receipt. Older unbound writer offers remain ordinary references; the original writer can answer again without an owner copying or republishing the bytes. On the normal permission-checked wake, reissue only the original task to the same writer, on its original generation. For a prose-only stop the operator must explicitly match the exact owner offer or fresh producer proposal in the native input form. Preserve the stop, check, scope, prerequisites, receipts and budgets. A preview or prior directory is not required. Record one fresh token and delivery before accepting work; an uncertain notice is not replayed.
   When the checked producer's native session has been reassigned, materialize a named file directly from an input already granted to this consumer. Require the confirmed pool handoff, exact original producer ID and candidate, signed component, applicable independent review, inclusion in the checked product, and matching regular blob in the consumer's frozen generation. Revalidate at delivery. Do not treat this read as a publication, revive the retired token, or involve the pooled session or either working copy. A previously unnamed stop requires a native match to the exact producer, path and blob; a bare claim cannot select arbitrary Git objects.
   A temporary join or permission wait keeps that reservation. If its inputs go stale or the joined check itself stops before delivery, withdraw only a provably unsent notice (including a confirmed-disabled preparation); restore the original stop and slot so other work can repair the failure. A previously approved match can continue without another dialog when its original pins return. Never withdraw an uncertain call.

   **Recovery selection is replaceable; authority is not.** A trusted edition's declarative rules map evidence facts to a proposal naming an existing operation, stopped attempt and immutable evidence. The operator can select the same operation directly. Only the operation can establish that its consent is satisfied and commit a reservation on live pins. Installing a selection rule neither changes the ledger nor grants a power; the existing owner wake can use it on an older stop. No project-loaded policy or new public command is needed for another combination of these facts.

   **The next action belongs in the responsible thread.** Use the native delivery journal to notify a proven writer about a linked goal failure, corrected task, read-only baseline, or approved observer preview. Deliver each material subject once on the current binding, including after upgrading an already-stuck run. An instruction uses no worker slot, repair or submission; a refusal or uncertain send is never replayed. Revalidate authority at the next operation. Scoped status shows who can act, wait, decide, or has no supported action, without disclosing writer tokens to other sessions. Derive saved-review recovery from typed obstacle facts rather than display wording; retain legacy interpretation for historical records. Writers prepare technical diagnostic inputs under their own access; the authorized approver sees ready-to-review operational arguments. An evidence request must not start its check.

   **Baseline group admission does not race release.** When the missing input is each original writer's own prior regular-file inventory, require the operator's bounded read-and-repair grant. A compatible signed checkpoint suffices while an unrelated product or goal call is outstanding. Bind approval to the named writers, original scopes, trees, target, evaluators and inputs rather than the brief instant between checks. Revalidate the entire group and the pending assembly before granting; never interrupt an issued check.
   **Continue only the frozen charter.** If the checked product has a newer charter at the same path, the existing reference or baseline form can present the exact old/new blob IDs and the separately verified read. The operator must explicitly approve keeping the old charter for the named original writer and task. No text comparison, matching offer, automatic confirmation or earlier target adoption decides compatibility. Keep every granted root, checker, boundary, supporting input and checked producer ID/version; check pending assemblies too. Neither identical directory bytes under another producer nor a removed dependency qualifies. Recheck the approved scope before delivering the fresh token; do not adopt the newer charter for the stopped work.
5. **Assess again.** A passing product check records the exact assembled commit, target, output pins, ownership and receipt. Reassess the goal on that commit, then admit the next evidenced work or qualify. Reproducing a failed tree with a fresh name is not progress. A goal run's `qualified` value remains null until both exact passes and release conditions hold. The owner receives the qualified SHA, not a branch update, push, export or archive operation.

**Evaluator boundary.** An exclusive runner claims only its own issued check. Materialize the pinned regular files, modes and authorized evaluator overlay in a disposable export; verify the export did not change. Invoke the selected evaluator without arguments. Component checks receive grain and directory/file scope; product checks receive the included outputs and exact ownership map, including exclusions. Goal feedback and changed paths are scheduling inputs outside the checked tree, never permission to skip a required observation. Preserve stdout/stderr and the actual numeric exit or null interruption.

Keep an approved change, its resolved verification inputs and the journaled attempt distinct. Resolve the immutable, data-only recipe used by the materializer; sign it in that attempt's receipt. Its commit, actual checker blob/mode and source, cumulative overlay paths/revision (including absences), and effective Foundry scope identify what the runner supplied. Each joined component has its own recipe. Bind calibration to the separate control executable and example. Identify supplied prepared bytes and private scheduling data by digest without disclosing their contents or ambient credentials. A check that was never reached has no passing observation. A recipe cannot authorize execution.

Reserve the intended role directly. The authority that admits the claim supplies any required live check for each execution step; the runner must not infer that policy from a checker filename or a list of recovery families. An already-claimed ordinary check on immutable inputs needs no later ledger read. For an approved serial change, a moved target or missing original predecessor receipt prevents key generation, not just key persistence. If the prerequisite disappears after the build, keep the earned claim and its signed interruption; do not start the evaluator or publish the batch.

| Evidence | Meaning |
|---|---|
| Component exit 0 | This grain at this candidate passed its selected check. A different tree has not passed. |
| Independent code review | `approved` permits publication of this exact passing component only. `changes` preserves the check and identifies a defect to repair; `unavailable` provides no code verdict. A writer cannot submit an approval. A baseline with no generated outputs has nothing to review. Runs activated before this requirement retain their original contract; never invent historical approvals. |
| Product exit 0 | The exact join passed its product evaluator. It is a checkpoint, not necessarily a goal verdict. A unique `FOUNDRY_REPAIR` on a failed product can route a repair only to an included owner. |
| Goal exits 0 / 1 / 2 | Respectively: goal met on the observed product; demonstrated gap; required observation unavailable. Other exits or interruptions do not establish any of these. An optional squad hint or historical attribution routes discovery, not qualification. |
| Owner handoff | For a goal, both distinct checks have completed, current, runner-owned exit-0 receipts on the accepted commit and corresponding evaluator pins. Owner status, dispatch and handoff recognize the same evidence. A stamped checkpoint with a current release hold remains a checkpoint, not a qualification. An old goal, a component pass, a native shell success, or a manually run alternate entrypoint does not qualify it. |

<summary>Receipt compatibility: signing bytes, binding order and duplicates</summary>

Only the exclusive claiming process holds the Ed25519 private key; the reservation keeps `runnerStarted` and the public JWK `x`. Select the signature binding from its validated attempt record, **not** the incoming row. An untagged historical document identifies version 1; on crossing, preserve that identity explicitly. The historical verifier retains the original bytes: SHA-256 of the old ordered binding, newline, and exact signed receipt document, including the optional evaluator pin and original pair, rerun, delivery, isolation, observer, production, calibration, test repair, rollout, foreground and replacement fields in their historical order. Never sign on behalf of an old claim.

For new reservations bind version 2, the original run/effect/issuer/call, nullable predecessor, exact native arguments, authorized use and immutable physical recipe in a distinct signing domain. Resolve the recipe outside the ledger write lock, after all members and their input versions are known but before the reservation is committed. Before claiming it, verify that its independent, historical, calibration or release role agrees with its scope. A passed or failed joined component can attest only its own ordered position and checker. Never reselect a different checker from the same path at execution time. Keep lifecycle updates, including a later inline repair, separate. Canonical object digests sort keys recursively and preserve array order. Store the signature as base64. A duplicate cannot replace a different receipt; an authentic late result belongs only to the original attempt and cannot undo a refusal.

The stored shell path, argv, quoting, shell ID and native arguments are an ABI. A matching original issued legacy command that reaches the upgraded path atomically closes its slot **before** a key, preparation or check. It exits 78, not a product verdict. An already claimed historical signer can instead finish or sign its own interruption. An eligible original issuer may reserve one linked new attempt only after proven non-issue or this closure **and** matching original native settlement. Revalidate authorization, target and use and require the fresh call's own permissions. Never infer permission, settlement or non-issue from a timeout, absence, shell text or a pending dialog.

The fence protects the original run ID, not the filename forever. A resume must find the existing ledger or stop, including when the file now names a different ID. Starting that different committed brief explicitly creates an independent run with no inherited assignments, receipts or authority. If the same owner has two runs at that path, require the run ID for resume.

## Recovery and changes in authority

For each stall, identify the existing obligation, the signal the original issuer can observe **after reload**, and the evidence needed to leave the wait. On a wake, re-read current authority and inputs before acting. Resume normal scheduling only for eligible work.

| Situation | Automatic behavior | What must not happen |
|---|---|---|
| Native writer start or notice has an uncertain reply | Watch for the original primary completion and re-read its history with backoff. Bind once when the request and result agree. Refill other ready slots independently. | No second start/send on silence, timeout, idle status or another issuer's evidence. |
| Independent code review is interrupted | Keep the exact passing component and review reservation. Reobserve an already bound workflow; use the recorded verdict after reload. Retain the finding, workflow identity and candidate on every settled attempt. | No publication on queue admission, missing results or ambiguous starts. A code review never substitutes for the product or goal evaluator, nor grants a one-shot or attestation writer another repair. |
| The issuer reopens while its ledger is locked | Back off and retry registering its observers on the same ledger. Once readable, find the original obligations without another chat turn. | Do not start a run, dispatch from the registration scan, poll a corrupt ledger, or keep a retry running after the session closes. |
| Scheduled reconciliation or a capacity check encounters contention | Keep the wake pending even if the notification was already received. Re-read eligibility on the original ledger after the lock clears. For capacity, only a confirmed pre-start rejection leaves an unbound review eligible to retry. | A queued wake is not a successful reconciliation. A timeout is not a freed slot and no issued launch may be replayed. |
| Check has no shell notification | Read the exclusive runner's matching outcome and continue from that receipt. Transient read contention retries the **read**. | No synthetic exit code, duplicate check or reuse of an unrelated pass. |
| Managed permissions return or a target ref reappears | Revalidate the issuer's hold token, mode, deadline, target and input pins. A transient mode-read failure keeps the watch alive without permitting dispatch. Independent history reads need not wait for an unrelated permission sample. | Do not clear an explicit pause, answer a question, repeat a dismissed dialog or silently adopt a changed contract. |
| A changed contract is the only remaining integration gate | On an ordinary owner wake, including the first after reload, preserve the checked product and prepare one proposal for adopting the exact descendant target. Show the conserved diffs from the contract and both evaluator pins, the included outputs, and any provably reversible unowned conflict resolutions. Claim the proposal before asking the operator to describe and approve the change to acceptance and prospective work. | No dialog for a participant, while frozen work is in flight, or for an unsafe merge. Status, resume, time, Autopilot and Approve All are not consent. A stale, dismissed or unconfirmed presentation cannot adopt or start a check. Never repeat a recorded refusal or duplicate a possibly live request. |
| An included component fails after target adoption | Compare the live target to the **adopted pin**, not the previous goal's target. A signed exit 1 identifies an observation, not a faulty file. On an owner wake, offer a unique exact diff either to inherited files or wholly to that failed output. Trace its assigning review or completed restoration; a directory match alone is not authority. For an owned edit show the old output, component, grant source, exact files, blob and new assembly. After fresh consent, the new output must pass its own component and the run's required code review. Replace just that pin before checking **all** components, product and goal on the changed assembly. | Never spend an attestation or old production/observer token, mix ownership, invalidate a pinned consumer, or overwrite conserved files, resolutions or target edits. A failed component, rejected or missing review, stale target or refusal cannot change the prior publication. Neither an artifact nor target approval grants an edit. |
| An approval has no visible form | Keep an automatic proposal ready while an owner turn is active or another native input is pending. Present a complete yes/no proposal in the owner conversation with just the native approval and decline buttons. Ask for a field only when the operator must supply information. A reattached primary owner can restore the same proposal only after its old presenter is gone and both the runtime and desktop confirm clear input queues. Retain the old presentation as lost and claim the new one before displaying it. | `presenting` means awaiting a response, not visibly rendered. Only an affirmative button response to the current confirmation approves it. Do not redraw a live request, infer a missing answer, or repeat a recorded refusal. An absent, unavailable or mismatched host observation cannot authorize a replacement. |
| A bound scout's outcome is unavailable | After a transient status-read error, observe that same issuer, dispatch and workflow again with backoff, even if the ledger has not changed. Keep the saved review intact. Only a verified halt for provider disconnect, current inputs and unused authority permit the original continuation. Journal its claim first. | A failed read cannot establish a halt. Do not retry a launch, repeat a claimed continuation, poll a permanent read failure on an unchanged ledger, or undo a pause. |
| An outcome arrives but the ledger write is locked | Keep the original result in the live issuer. Recheck the still-bound workflow, or retry only the conditional write for the exact native call or owner presentation. | Never resend a request or overwrite a terminal reply. After issuer loss, use matching native history where available; a same-session notice has no such history. An unrecorded dialog answer needs explicit recovery, not reconstruction. |
| An independent checkpoint advances | Keep compatible reservations, drafts and published outputs. Revalidate affected consumers; route an eligible remaining repair to the original writer. | Do not discard all work, transfer ownership, or treat unavailability as success. |

## Observable surfaces

On issuer recovery, read the original native history once per sampled set of calls. Match each primary call's own ID, arguments, turn boundary, completion and refusal independently. A missing or ambiguous match is never a new launch. A recovery-only status read must preserve scoped actionable guidance without constructing the historical report list. Keep complete proof available separately. Acceptance: reload two uncertain starts with opposite outcomes, observe one history traversal, and confirm that the bound writer and refused sibling retain their distinct original results.

Apply the same ownership rule when binding a native workflow and when reopening its ledger. Multiple scouts may share one workflow only within the same issuer and dispatch. Previous reviews and completed authors retain their identities. Reopen a valid shared scout batch; a conflicting stored dispatch must refuse status and resume without changing either original call.

Hand the native adapter only the ticket selected by the committed ledger revision. This also applies when observing a workflow needs no document change: if another connection pauses the run between selection and commit, reselect and return no stale ticket. Keep the observed workflow and its original call unchanged.

**Tool selection.** Owner requests for a scoped review, a fresh check and exceptional writer access each have one native entry point: `foundry_review`, `foundry_check` and `foundry_grant`. Each takes `run` and **exactly one** named object containing only that operation's inputs. There is no default operation or flat fallback. A queued review note cannot start discovery; a preview cannot submit; publishing a reference cannot authorize baseline inspection or repair. Keep each variant's issuer, evidence, approval, capacity and revalidation rules. See the [tool selection guide](PROTOCOL.md#choose-a-foundry-tool) and the exact schemas in `spec/interface.json`.

Status is a read, not a scheduler tick. An owner can distinguish reservation, uncertain launch, confirmed binding, pending check, signed outcome, checkpoint and qualification. A participant sees only its scoped work; previews, references and private owner proof are not interchangeable. Host-reported usage with missing coverage is **unknown**, not zero. Export and cleanup are separate operator requests; neither follows automatically from qualification.

On explicit owner proof inspection, verify the exact accepted signatures and Git sources. Export those verification inputs for every included observation; never reselect them from a working tree, today's checker or a net diff against the contract. A recipient can materialize them without the source ledger or executing product code on import. Label a recipe proved from older immutable witnesses as reconstructed, not signed. If inputs cannot be established **or represented**, report the portable record unavailable without rewriting history, replaying a check or changing a verdict. In particular, v5 cannot carry an old runner's privileged foreground environment for a standalone or joined component, even when no preparation hook ran. Native issuers, call IDs, writer tokens and signed diagnostic output stay out of the exported manifest.

Record its parentless carrier and tree OIDs and each cumulative overlay path's mode/blob or absence. Bind the carrier to the physical description, not the other way around: original source commits remain provenance. Pack and import each verify the entire transferred object inventory against the allowed closure in an empty isolated store. No private feedback or ancestor history is inferred into that closure. Original-commit transfer requires a separately selected, warned history mode; never fall back to it. The neutral, distributed physical materializer is shared with the runner. The offline CLI writes to a new private destination and describes the ordered build, verified copy, component, product and goal launches without executing any. A private scheduling digest cannot recover the required bytes.

The default replay selection is the release; original standalone captures require explicit selection. Materialize in a fresh private staging area outside Git worktrees/metadata and ancestor Node `package.json` or `node_modules` contexts. Choose a clean parent for any other tool the evaluator uses; the helper does not detect every toolchain's configuration. A v2 launch description binds an exclusively created empty private feedback file at the last verification before the goal, never adopts or truncates a prior step's file. Recreate older descriptions from retained carriers, not by rerunning the original ledger. A separately authorized replay must give builds and checks the runner's noninteractive standard I/O: ignore stdin, pipe and preserve stdout and stderr without a default output cap. Describing a launch must not execute it or change a deadline.

**Work graph — what is this assignment for, and whose output does it use?** Select a node to read its assigned task before checks or diagnostics. For a fixed grain without task text, identify the specification and let the viewer request its actual text at the assigned base (the contract base before staffing). Resolve the grain under the viewer's *current* scope on every read; never accept an arbitrary path or substitute working-tree bytes. If the text is missing or unreadable, say so. Do not invent a purpose from the ID, a blocker or a neighboring node.

Show the run phase separately from the counts of visible assignments. Keep the text readable without color and wrap counts rather than truncating them on narrow panels.

A checked prerequisite differs from a pending one; an observational rerun alone does not make it usable. Search and trace must not change readiness, pull unrelated sibling branches into the trace or reveal hidden producers. Preserve selection and navigation across live updates while the assignment remains visible. If access or the read fails, do not present stale evidence or substitute a demonstration. Examples must be explicitly selected and labeled.

Dependency arrowheads point along the last visible stretch of the connector and end at the consumer's boundary, in either orientation. A diagonal approach keeps its direction rather than snapping to the layout axis. On a link that skips ranks, use the final routed stretch, not a bearing from the producer's center. Keep the full head outside the card.

**State explorer — why does this state exist, and what can move it?** Use the same definitions and interpreter as the runtime. Show a state's purpose on selection; for an event, explain the selected outcome first and disclose ordered alternatives, guards, actions, admission and diagnostic on demand. Descriptions must be accessible without hover. An enabled event on an arrow advances the local configuration; inspecting a state, event name or inactive branch does not. Deliver one event to all participating parallel regions. Rewinding restores both state and guard inputs; sending again branches only the simulation. No simulated action may invoke an effect or read a live run.

Both layouts are first-party and offline. **Work dependencies are soft curves:** ease out of the producer, stay within the space reserved around intermediate cards and meet the consumer along the final shaft. Rank jobs by declared inputs and place short branches near their consumers when space permits.

**State transitions are straight runs with locally rounded corners, not work-graph splines.** Arrange the forward lifecycle in ranks, keep branches and joins together, and reduce crossings on both sides of each rank. Align long returns in parallel lanes where their order is compatible. Where several lines approach one state from the same side, the inner rail turns sooner, farther from the state, with a tighter corner. The outer rail runs closer before turning. Leave visible space between their diagonal approaches up to distinct ports, even if a loop occupies the neighboring face. Apply the same geometry when the diagram rotates. Round each visible fold locally with a quadratic Bézier, trimming at most nine graph units from either leg; don't double back at a label or skim along a state's border.

Break cycles for placement only; preserve every rule's direction and priority. Reserve room for each bordered event label on its own line, including inactive `pause` and `resume` labels. Self-loops return locally to distinct ports on their own state; targetless actions stay inside it. Bundle only rules with identical source, event and destination. Hovering or focusing a label traces that line without firing it. Keep states and labels unobstructed in narrow panels and parallel frames. When fitting makes labels too small, open around the selected state at a readable scale; offer an overview and direct state selection without moving the actor.

## Keeping the specification current

For every change to Foundry, compare the intended result with this contract **before** editing and again before handoff. Change the relevant requirement, interface data, and acceptance case in the **same changeset** when behavior, architecture guarantees, authority, durable data, signals, evaluator semantics or user-visible interactions change. If a fix restores an already precise requirement or a refactor leaves it intact, name the unchanged clause and the evidence; do not rewrite the requirement to excuse the bug.

From the repository root, `node --test .copilot/extensions/foundry/test/interface.test.mjs` compares the registered host interface and machine definitions with the reviewed JSON. `node .copilot/extensions/foundry/test/interface.mjs` prints the current declaration as a **candidate** for review; it does not update the spec or start a run. Review the semantic diff and adjust the prose and controls before accepting a changed declaration. This check detects structural drift, not a wrong guard implementation or a missing behavior; those need the independent cases above.
