# How work reaches a writer

A scout [proposes work from evidence](#propose-work-from-evidence). A bound writer [builds the assigned output](#build-the-assigned-output), then [submits it or reports the exact stop](#submit-or-report-a-stop). Read the section for the role you actually hold.

## Propose work from evidence

**Discovery:** Foundry gives each tool-less workflow scout the pinned evidence, goal diagnostic and relevant assignments. Its one structured report may propose `{id,task,directory,check,needs}` in an area charter. Fixed charters request owned IDs only. No scout session, token or tool call is needed.

**Shared brief:** When all area squads omit `boundary`, each gets the full `.foundry/<plan>/journey.md` and the names of other committed regular files. Names are not evidence. Use `needs-evidence` to read a file from the reviewed tree; follow references with further requests for distinct paths. A cited file inside a declared prerequisite comes from its checked output, not an older scout read. Other requested, cited files outside your assignment are read-only at the named `revision:path`. This does not expand your assignment or permit reading its prior implementation.

Foundry checks those frozen inputs against the assembled product when admitting your output. A changed or deleted input can exclude the output without erasing its component receipt. An older kickoff that explicitly named contradictory versions is not reinterpreted after reload. On an unmet goal, a fresh review of the changed input can `replace` the excluded assignment with a new ID for the same scope and check. A later edit does not invalidate an output already admitted to a checkpoint; put enduring relationships in the goal evaluator.

**Pre-writer research:** Only an area charter that names a `researchAgent` can request `needs-research`. Put the question that would change the writer decision in `reason`, cite the charter evidence, and use `grains: []`. Foundry dispatches the named profile separately under host permissions. A scout reviews cited findings even if the overall answer is unknown. Assign the independently supported work and leave the rest explicitly open; if there is none, report unresolved. Writers receive the same charter's findings and limitations. Research cannot qualify a product. Do not send private source or credentials to outside services.

Publish a shared reference as `references: [{repo, revision}]` as soon as the sibling checkout name and full commit are known. There is one commit per repository for the run. To inspect it, use `waitFor: "reference:<checkout-name>"` (`waiting` for a scout; `unknown` for a researcher) and state the question. A bare charter ID waits for finished output, not a pin. Use the published commit and an authorized immutable reader; a matching checkout HEAD alone does not establish which bytes you read.

**Before making B wait for A:** Name in `reason` the exact checked output A must supply and what B cannot start without it. If both can start from the committed interface in disjoint directories, propose both now with no dependency between them. If only the integration needs A's output, split that part out and give it the dependency. Shared writable files aren't a reason to race two writers: split ownership or keep one assignment. Every `needs` ID must already exist or be in the same batch.

Check the reverse, too: could the writer complete the stated behavior with the assigned directory removed and only its permitted inputs available? If it needs another writer's output, name that producer. If it needs prior bytes, a read grant or an external resource, identify that requirement separately; don't invent a producer edge. Write `task` as the behavior the assignment exists to deliver, not a status, filename or list of steps.

Use `replace` for unstarted work. A milestone preserves the tree, not its assignments: reuse or split qualified outputs. Repeated or blocked area work can trigger fresh discovery on the same revision. Never displace a live assignment or its inputs, or retry refused work.

When two directories must change together, propose e.g. `"directory":["codec/decode","codec/encode"]`, not `"directory":"codec"`. List only complete, disjoint directories in the same charter and select a check that exercises them together (`FOUNDRY_DIRECTORIES` is a JSON array). A sibling such as `codec/checksum` stays available. A fresh review can withdraw an untouched, never-issued start with `replace` and new IDs; after dispatch, do not change the set mid-assignment. Repartition after a passing product checkpoint once any consumers have released their pins. A pooled session keeps its conversation, not its former directories.

On a source-backed comparison with approved integration files, propose exactly the supplied set, e.g. `"directory":{"primary":"codec/labels","files":["codec/views/index"]}`. Generate the complete primary directory and edit the named files in place at their frozen versions. They must remain regular files; no addition of siblings, implicit deletion, symlink or directory substitution. `FOUNDRY_DIRECTORY` names the primary check directory and `FOUNDRY_FILES` is a JSON list of the exact files. Submit all changes together under one token.

If your packet marks a terminal assignment `supersededAttempt`, its original writer cannot use retired prerequisites. If current evidence still warrants that work, propose a single fresh ID with `replace: [oldId]`, the same directory and check, and qualified current inputs. Retain the still-current original pins and explain why the replacement inputs are needed. Do not request another check of the old candidate.

**Report:** Cite only file contents delivered in your packet. A complete packet may support `no-gap`; a partial one can support a specific change, not an exhaustive conclusion. To read more, return `needs-evidence` with one `file`, `receipt`, or `detail` selector from the packet. Add `match` to search for literal text instead of paging to EOF. Use `offset` equal to `hit + 1` for the next match, or drop `match` and use `end` as the offset for the next page. Do not repeat a read that made no progress. Diagnostics and owner questions are context, not file citations.

On a scoped comparison, read the selected reference text or request its `detail`. Only the pinned product can corroborate it; binary content is not a text observation. If an already-bound task conflicts with the frozen product, flag the exact clause instead of implementing a workaround. After an approved `foundry_correct`, read your own `foundry_status`: the node's `task` is current, and `correction` identifies the removed clause and cited excerpt. Keep the same worktree, token and read/write boundaries. The excerpt does not grant access to its source file.

If no independent work is possible before another area charter produces a checked output, use `waiting` with `waitFor` set to that charter's ID. Use `unresolved` for missing facts. Use `needs-decision` only for a product choice or external action only the operator can take; set `ownerInput` accordingly. These non-writing outcomes take `grains: []`. Do not change checks or start sessions. A single `FOUNDRY_SQUAD=<id>` goal hint can focus discovery; an unproductive hint falls back to the other charters.

## Build the assigned output

Generate the **complete** assigned directory at its frozen base; omitted files are deleted. For independent pieces, launch native `task` agents in parallel **in this worktree**, not new desktop sessions. Give each disjoint files or a read-only question, the permitted inputs and the assignment constraints, never the token. Ask for results, not further delegation. Keep shared files for integration. Work solo for small changes or when helpers are unavailable. Neither writer nor helpers may change contracts or evaluators, switch base, commit or land.

Keep the Git branch the host assigned to this worktree. Neither you nor your helpers may rename it with `rename_branch` or Git commands. Use `rename_session` for a readable title; it does not change Git refs.

**When the assignment changes Foundry itself:** use the [framework spec](../../../extensions/foundry/SPEC.md) at your approved revision, not a newer installed copy. Identify the affected clause and acceptance case. Include the spec change if it is in your grant. Otherwise give the owner the exact required change for a separately scoped documentation edit; do not widen your grant or declare the framework change complete without it. In a blind rebuild the reviewed spec is an input, not something to amend to make a check pass.

**New assignment in a reused session:** call `foundry_workspace({run,token})` with the **new message's** token before editing. Reload this session's extension first if stale. Use the returned node's `workspace` as the root for every path, command and helper. Preview, publish and submit use that checkout automatically. Never move the old branch, copy the old directory, or reuse an earlier read grant or passing result. Reopening the same workspace after reload does not reset your edits. If the checkout can't be verified, stop and report the error; don't submit from the outer worktree.

For an approved `reuse` successor the worktree already contains the retained candidate directory. Keep its working behavior and inventory, inspect the named correction blob, then make the in-scope fix. Submit under your new token and identify the reference actually used. The old token and failed receipt are historical; you do not have another repair allowance.

For a **narrow successor** named by a source-backed review, the opposite applies: the checkout contains the approved *current product*, including its primary directory if it exists. Change only the named directory and exact integration files. Do not read or import the stopped assignment's candidate, preview or local edits. The old stop is not a passing check or permission to repeat the old observation. An unchanged submission does not start a component check.

For an **ownership restoration**, the checkout also contains the current primary, but this assignment must submit it **unchanged** for its own fresh check. Leave every integration file with its existing owner. Do not copy a historical tree or edit the code to make the check pass.

If your launch is uncertain and `foundry_status` says you are unbound, keep the directory and use the [existing writer recovery](runs.md#recover-an-existing-writer). You need only your original kickoff token, not a grain ID from the coordinator. A child claim alone does not authorize submission.

For a midpoint comparison, join helpers and call `foundry_preview({run,token})` before submitting. Give the owner your node's `preview` commit, the one behavior or scene to inspect, and the reference version. Keep working on the same token. Change the implementation before repeating an unchanged comparison; don't replace it with a release sweep. A preview is a draft, not a verified product or permission to inspect another worktree.

For an interaction repair, use one case that reaches the failing action through the implementation the product actually invokes. Preserve the starting state and any effects that must **not** occur. A fixture can isolate a boundary, but it cannot prove that the integrated path uses it. Report the first comparable result, its build and what it did not exercise. If the required observation is unavailable, say so; a successful build is not a substitute.

A pending release check is not a dependency of a bound checkpoint writer. Work on the assigned directory and frozen prerequisites. If it needs a different version or another team's unsubmitted output, report that dependency; don't switch bases or borrow permissions. A green result for the older product does not cover your change.

A passing goal waits for reserved work (including a held or unconfirmed call), a fundable next step, or integrable output. A stopped or refused advisory comparison, or one that needs a reservation the run cannot fund, does not hold the unchanged checkpoint. This does not waive a required check or any seeded one-off output.

For charter-authorized maintenance, use `directory:"path"` for the accepted copy at kickoff or `directory:"<full commit>:path"` for an expressly permitted pin. The output is always `path`. The kickoff and `priorSource` in status identify the exact revision and tree; neither is a read grant. If permitted, read individual files with `git show <revision>:<path>/<file>`. Do not refresh from `HEAD`, consult siblings, or search for a different version if the directory is missing.

New scout proposals classify that prerequisite: `prior:"independent"` needs no removed files; `prior:{clause}` cites the owning charter's explicit read permission verbatim. If the required permission is absent, report the missing prerequisite rather than proposing the writer. `prior:"unavailable"` cannot staff one. The citation is checked against delivered charter text and the directory against the reviewed tree; a matching quote is not itself permission.

For an array, use the same revision for every root. `priorSource`, `readGrant` and `baseline`, when present, list the pins that exist. Generate and submit **all** assigned roots together; omitting a previously populated root deletes it. If any part cannot be produced from permitted inputs, report `missingInput` instead of submitting a partial output.

**Late references:** The owner can publish an explicitly selected file with `foundry_publish({run,file,to})`; a writing producer includes its `token` and can publish only from its assigned directory. `to` names the intended output directories or charter areas, including the reviewer's. A running writer gets a notice; future matching writers get the reference at kickoff. Use the `extract` command in `foundry_status.artifacts` from your worktree to open the exact version outside the product. Report the blobs you actually used (`usedArtifacts`) or compared against the product (`comparedArtifacts`) on submit. Receiving a file isn't a comparison, and a comparison can reveal a mismatch. If the required observation can't be made, leave it unverified.

If a specific reference is missing **before submission** and you know its full Git blob ID, use `foundry_submit({run,token,missingInput:"what is missing",inputBlob:"<full blob ID>"})`. If you know its producing assignment and path, also supply `inputSource:{grain,file}`. Don't guess. The original producer can answer directly; a checked prerequisite must supply the exact file from its checked version. Wait for the fresh assignment notice and check your own status for `suppliedInput`; your original token stays stopped. No live sibling checkout or prior tree is granted.

**Answering as the producer:** use `foundry_publish({run,token,file,to:["requested-output"],forInput:"consumer-grain"})` with your own token. A checked source is extracted by Foundry; do not copy it into another checkout. For a working source only your granted regular file and the exact requested blob qualify. You are supplying a read-only reference, not granting a dependency or changing the other writer's task.

## Submit or report a stop

A `Foundry instruction` is a notice for your thread, not a new grant. Read `foundry_status({run}).recovery` and match its ID before acting. Check your assigned checkout, current token and allowed files. A stale notice, read-only status, or pending check does not permit editing. A `diagnosis` asks for technical evidence, not a product change. Use `foundry_propose({run,token,check,observe:{harness:[...],current:[...]}})` for an original stopped component, or the named `observer`, `production`, or `footprint` form for that evidence. Report only permitted sources. Foundry addresses the resulting decision to its owner; do not send an owner your token, write an owner-side patch, or rerun the old check.

Only the bound writer calls `foundry_submit({run,token})`. Collect every helper, check its changes and finish missing pieces before submitting. A refusal lists the running task IDs; the same token remains writable. A verified independent Foundry scout or researcher running in the writer's session does not hold up submission. A failed evaluation returns a fresh token for a bounded repair or a blocker. Repair in the same worktree; don't repeat finished slices. Do not claim success or supply an alternate check. For a permission hold or an uncertain native call, follow the [run recovery rules](runs.md#pause-and-resume).

**Cannot produce the complete directory from permitted inputs?** Do not submit a partial or empty replacement. After joining helpers, call `foundry_submit({run,token,missingInput:"what is missing and why the authorized inputs are insufficient"})` from your assigned worktree. This ends your writable attempt, **without capturing files or running a component check**. It is not a request for read permission or a mechanism for resuming that token. The charter can review the blocker and request permitted evidence or propose independent work; if no permitted route exists, report the gap as unresolved.

**After a component passes**, a new run automatically requests independent Rubber Duck code review. Do not start a reviewer yourself or resubmit while `reviewing`. Read `nodes[].codeReview` in your own `foundry_status`. If it requests changes and your state returns to `writing`, use the current token to address the finding in the same worktree and scope. Submit the changed output for a fresh component check and review. A blocked or unavailable review is not permission to change an attestation, skip review or publish an output.

**A checked repair would repeat a prohibited observation:** Read your own status. If the node is `writing` and shows `cannotRepair`, join helpers and submit `{run,token,cannotRepair:{check,reason}}` using its current token and `cannotRepair.check`. Say what was observed, what is still unknown and why the original assignment permits no further repair. Do not end the turn with a writable token and only a chat report. Foundry preserves the exit-2 receipt, tested bytes and any preview; it does not capture edits, repeat a check or grant reads. A genuinely permitted repair still uses the normal submission path.

**No scoped fix or missing input remains:** If your own writable node shows `relinquish.check`, use `foundry_submit({run,token,relinquish:{check,reason}})` from the original worktree after joining helpers. Copy that exact check and explain why no scoped repair remains. This records a distinct writer stop, not a missing input or an inconclusive verdict. The signed numeric failure, tested commit and preview stay in history; unsubmitted edits are not captured. It cannot retry a check, clear a pending call, release a product or grant a successor access. A later successful observation is not evidence for this check.

Scouts see `stoppedRepair` on the owning charter's graph. Use its `detail` to read the original diagnostic if needed; cite the delivered product files, not this metadata. Propose disjoint work, or one **different** task for that exact directory and check with a new ID and `replace:[oldId]`. A successor starts from the reviewed product, not the stopped candidate. If no permitted change or observation follows, report the actual prerequisite as unresolved.

**A missing preservation baseline:** Flag missing input in discovery when possible. If already stopped, read your own `foundry_status`. A `readGrant` permits inspection at exactly its `revision:directory/`, not editing or submission. The owner can request `foundry_grant({run,inspectBaseline:{grains:[assignmentId]}})` for inspection or `foundry_grant({run,repairBaseline:{grains:[assignmentId]}})` for a bounded repair. An unrelated product or goal check need not finish first when the signed checkpoint and your pins are compatible. Only act on the fresh writable attempt and its `baseline`. A `priorSource`, file offer, or chat message by itself is not approval.

If an older incomplete component check left you blocked, read your own `foundry_status`. Only if your node has `changedFrom` and you have a correction within the original assignment, apply it in your assigned directory and call `foundry_submit({run,token,changedFrom})` using the exact status fields. This spends a bounded repair on new bytes. Do not rerun the old candidate or substitute an outside check. If no slot or repair remains, or your inputs changed, report the blocker.
