# Measure one Foundry run

Ordinary status already reports binding and qualification latencies; answer timing questions from those facts when sufficient. **Only for an explicit usage or hosted-kickoff report**, read `foundry_status({run, detail:"usage"})` once in the owning session. Use its private `metrics`, not a factory with a similar name. Never include the identity/history projection in a portable qualification record. Don't start or resume a run, launch helpers, poll for completion, or export a transcript.

| Question | Evidence to report |
|---|---|
| How soon did a writer receive its assignment? | `first_hosted_kickoff_elapsed_ms` in the history query below: from confirmed activation to the first **host-recorded writer kickoff**. This is the timestamp of the exact assignment's `user.message`, not session creation, a first token, or proof that code was written. |
| When did Foundry confirm the first binding? | `metrics.firstWriter.elapsedMs`, with its `nativeIds`. This includes pauses and can be **hours later** if a lost `create_session` response was recovered. A reservation, kickoff request, scout, queued message or `writing` node is not a binding. |
| How soon did the exact product qualify? | `metrics.qualified.commit` and `elapsedMs`. For a goal, the finish is **acceptance of this commit** with both passing checks, not publication of an earlier checkpoint. Without a goal, it is publication of the reported passing product, not termination of ongoing discovery. |
| What if a milestone never happened? | A no-writer baseline can qualify: report **“no writer required”**, the accepted baseline SHA and its qualification latency. The baseline is the assessed target tip, not necessarily the contract's `base`. Otherwise distinguish `not-bound` from an unconfirmed native call. A null qualified commit means **not qualified**; a known commit with no clock means **time unknown**. Neither is zero. |

### Read kickoff timing and observed model usage

1. Use the [read-only query builder](../scripts/usage.mjs). It reads JSON from standard input and prints a native `session_store_sql` query, **not** a usage estimate. From the skill base directory run `node scripts/usage.mjs`. Supply `{"metrics": …}` using only the owning status's `metrics` object. For an unfinished run, also give `asOf` as the UTC epoch millisecond of that status snapshot and label the report **through that instant**. It is not a qualification time. A qualified run always uses the qualifying product's clock instead.
2. If the builder returns `query: null`, report the reason. Otherwise run its single exact query with `session_store_sql`, `source: "cloud"` (personal scope). Read only the cloud result; local history IDs are a separate namespace. No raw prompts or submit tokens need to leave the session; the query compares message hashes in the native store. No read of the Foundry SQLite file or application data directory is required.
3. Read `hosted_kickoff_elapsed_ms` per writer even when there are no usage records. `first_hosted_kickoff_elapsed_ms` is the minimum only if **every** confirmed writer has a verified kickoff and no creation is unconfirmed. With missing, ambiguous or partial history the run's first kickoff is **unknown**; don't substitute the earliest visible row or the binding latency. No writer was required on a qualified no-writer baseline.
4. Show the `observed writer-session usage only` rows **by native writer and model**: usage records, input tokens, output tokens. A measured zero is a number; a null is **unknown**. Preserve unresolved writers and missing counters alongside measured rows. Cost, credits and cache usage are unknown; don't infer them from token counts.

**Attribution rule.** Use confirmed writer effects, including retired assignments. A native identity must resolve uniquely to a newly created `sessions.id`, directly or through `sessions.task_id`, and the *exact* Foundry kickoff must appear in that history. Task IDs, local IDs, workflow IDs and cloud history IDs are not interchangeable. Count `assistant.usage` records in the verified writer session only after kickoff, at or after binding, and through the exact cutoff. The first different user input (even a repair), system notification or session resume ends attribution **before** that instant, including ties. Do not reopen that window, pool results from different sources, or use a name, branch, approximate kickoff, or coincident timestamp to guess a link.

**Coverage is not a run total.** A shared owner's time in this window is not proof of run work. The subtotal can include calls surfaced under a writer session; it cannot separate embedded helpers. Separate helper usage and scout/workflow usage are **unknown**, not zero, unless the host supplies usage explicitly linked to the actual task or bound workflow run (`metrics.history.workflowIds`). If such a native receipt is available, label its scope and units separately; don't add it to session events without proof the two sets are disjoint. A budget, helper count, elapsed time or successful scout report is not an accounting receipt.

`session_usage` is **lifetime per session/model**. Filtering `last_used_at` only selects whole aggregate rows. Do not use it to fill a hole, subtract unrelated history, or prorate by elapsed time. The local store lacks the cloud `events` table; an unmapped ID, absent/rewritten kickoff, unsupported schema, retention gap, missing counters, or backend error means unknown. Do not widen the search or assume absence of foreign inputs across a known gap. The query aggregates before the 10,000-row native limit and emits a diagnostic instead of a clipped total. If the returned row count still differs from `result_rows`, treat coverage as incomplete.

Example wording (illustrative only): “First writer bound after 9 s. Checkpoint `…` passed; the goal has not qualified. Through 14:30 UTC, writer A has 3 observed usage records on model M (1,200 input tokens; output unknown). Writer B could not be mapped. Total run usage, including separate helpers and scouts, is unknown.”
