## Find a plan

Run `node <skill-base-dir>/scripts/plans.mjs` from the user's checkout for `plans`. It lists short names for top-level `.foundry/*.json` files at `HEAD`, not uncommitted drafts or running factories. Listing a filename is not a readiness check.

For `start`, pass the operator's target as one literal argument to that same [read-only helper](../scripts/plans.mjs). For example, `catalog` resolves only `.foundry/catalog.json`; an explicitly supplied repository-relative `.foundry/...` path is also accepted. It returns the canonical `source`, actual `run` ID and `target` after checking the committed contract, its pinned files on the target, and any pending edits to those files. It does not run evaluators or open a ledger. A filename and a run ID can differ. Don't substitute a run ID, fuzzy match, different branch, or uncommitted brief for the requested source. On error, report it; offer `plans` for a missing name. `resume` looks up an existing run instead, as described below.

## Start

Repeating start returns an existing active or qualified run without advancing it. It cannot lift a pause. To continue existing work use [resume](#pause-and-resume) only on explicit direction.

On direct operator direction in the interactive or Autopilot owning session, pass **only** the resolved `source` to `foundry_start({source})`. The explicit start or resume request authorizes the named committed brief; do not ask for a second confirmation. An installation, schedule, child kickoff or queued message is not authorization. Neither the request nor Autopilot grants tool permissions. If managed settings are unresolved or the session uses Manual approvals, relay the blocker; Assisted is sufficient if policy permits. Don't start replacement workers.

Do not ask in chat to reconfirm routine recovery. In Interactive Assisted, Foundry asks when access, ownership, the assigned task or evaluator changes, or an input classification needs judgment. **Autopilot** and **Approve all tool calls** omit eligible yes/no forms when policy permits; [mixed target adoption](#mixed-target-adoption) still requires explicit operator confirmation. Operator direction and host permissions still apply; a product question still needs an answer.

Report the **returned run ID** for `status` and `pause`, and the actual state or blocker. An ordinary repository session owns the run; no Copilot app Project is involved. One start covers the goal. Checked milestones don't need new plans; scouts revise the work. `limits.workers` caps concurrent scouts and writers, not native helpers. Existing version-1 fixed contracts still work; `seed` without `goalCheck` is for an explicitly requested one-off.

## Checkpoint triage and repair handoff

When driving an authorized run, revisit the **whole brief** on a new checkpoint or receipt, when a repair stalls, and when returning to the run. Read the latest checked product, receipts, pending calls and assignments. A failure on a writer's frozen inputs is not necessarily a defect in the current product. If even a passing brief would miss the agreed outcome, identify the contract gap for the operator; don't silently change the finish line.

1. **Find the first observed mismatch.** Keep the revision, receipt, starting state, ordered actions and actual result. Group failures only when the state, actions through failure, and symptom match. Diagnose that prerequisite once; distinguish later steps *not reached*, journeys *not run*, and older failures *not re-observed*. Keep independent discovery and repairs moving in parallel.
2. **Route it when its inputs are ready.** Trace the failing behavior to the implementation the checked product actually uses. Match each open repair to its directory, required input and existing review or writer. At the first passing checkpoint containing that input, give the evidence to the matching writer or request an eligible scoped review under the [admission rules](#status). Don't wait for an unrelated release check. Follow an outstanding review or launch rather than issuing a duplicate; a note, offer or review request is not a repair owner.
3. **Reconcile a stall instead of waiting for another checkpoint.** Compare the assignment and last receipt with the bound session's actual activity. If an idle writer can take a specific next step on its existing assignment, contact it once. If a review was blocked, use the applicable [recovery procedure](#pause-and-resume) on the original ID. Respect approval and capacity limits. Report the exact remaining blocker if recovery cannot proceed; do not restart an uncertain call.
4. **Close only the failure the evidence settles.** Before requesting another diagnostic, name the decision it could change. A matching failure receipt is already a baseline; do not reproduce it on unchanged inputs just to get another red result. Pair it with the observation of the same action, relevant state and expected outcome on the repaired product. If the action passes and the next one fails, close the first finding and record the new one. Report the user-visible change separately from evaluator improvements and outstanding release evidence.

## Status

Use `foundry_status({run})` with the run ID from the start receipt. This reads state without advancing it and does not require a clean checkout. `checkpoint` is progress; in a goal run `qualified` stays null until both committed checks pass on the same exact commit. The target branch stays unchanged. Report concrete blockers or contract questions, not a completion claim.

In new runs, `reviewing` means the component passed but its candidate cannot yet be used. `codeReviews` records the independent Rubber Duck verdict; `reviews` records charter discovery. Check the original workflow in `detail:"proof"` rather than asking a writer to review its own submission. Only an explicitly resumed, confirmed unavailable attempt may start a fresh review of the same pins; a missing start reply is not such evidence.

In the desktop app, open **Foundry** (`canvasId: "foundry-board"`, `input: {run: "<run-id>"}`). Reuse the same panel handle for this run. For a text-only request, summarize the same status in chat. If the run is inaccessible, report that; don't substitute another run. `{example:true}` is an explicitly selected demonstration, not live evidence.

Select a node to read its purpose, or open its **assigned specification** for a fixed grain. **Trace selection** shows the declared producer outputs and visible consumers. A node with no edges may still need a read grant, an undeclared output or a shared resource. **Find** searches all visible assignments; **Run** shows checkpoint, goal and questions. Open **Assignment evidence** for exact scope, evaluator and pins.

On qualification, hand the owner the full `handoff.commit` and checked target. Keep writer sessions. Use the [handoff guide](handoff.md) for portable proof or separately requested cleanup. For model usage use [`/foundry measure <run-id>`](metrics.md); missing observations are unknown, not zero.

### Comparison and repair procedures

Status alone authorizes none of these operations. Choose the procedure that matches the observed obstacle and the operator's request.

`foundry_review`, `foundry_check` and `foundry_grant` each require `run` plus exactly one named form. A file offer is still `foundry_publish`; a note for the next ordinary review is still `foundry_review_note`. For earlier tool names in a saved diagnostic, use the [selection and migration table](../../../extensions/foundry/PROTOCOL.md#choose-a-foundry-tool) with the existing pins.

This read neither resumes the run nor clears the recorded hold; don't retry to find out whether settings loaded.

Changes affect future admissions only. Don't pause or replay work to apply a setting. The read-only `release.reason` explains the release gate, not whether an individual writer is bound. A missed shell notification can heal from the exclusive runner's exact receipt; an uncertain call without evidence remains uncertain.

Route a concrete mid-run mismatch to the **production directory**, not another audit. Give a bound writer the comparison only if its existing task and pinned inputs cover the change. For distinct work, preserve the reservation, candidate and original check. A refused comparison queues nothing; once the directory is available, request a fresh comparison on the then-current product. Call `foundry_review({run,compare:{directory,receipt,blob,question}})` with the offered blob and observable change. On a settled unmet goal use its goal check ID. If that checkpoint's goal is still issued or uncertain, use the latest passing `products[].check` ID in status, including while a superseded evaluator finishes. This pins the work to that product, not to a supposed goal result. Use only inputs already checked there; stop if the owned directory or required inputs changed. Do not restart, repin or replay a goal to get a writer.

If a scoped comparison **already has a bound writer** whose task contradicts the frozen product, don't iterate again. Read the node's `review`, `worker` and `task`. To remove one contradictory clause from that original, unsubmitted assignment, request `foundry_correct({run,grain,review,worker,clause,file,excerpt})`. Use the assigning review, not its `iterationFrom` ancestor. Quote the exact clause including whitespace, and a verbatim excerpt from a regular UTF-8 file on the reviewed product. The operator reviews the before/after task; do not approve on their behalf. On approval, tell the **same writer** to reload if needed, read its status and work under the original token. No chart, receipt, file offer or chat message authorizes a contract change. Never repeat a declined or uncertain correction; inspect status first.

The same request works for an original ordinary single-directory assignment. Its frozen citation is owner-only, even when the file lies outside the writer's grant. If that writer already stopped via `missingInput`, with a preserved preview and **no** component verdict, also pass `preview` with that exact commit. Wait for a settled unmet or unavailable goal and a free repair slot. Approval delivers one repair to the same writer and worktree; use the new token after confirmed delivery. No new discovery, file read, or checkout is implied. If evidence or owned inputs changed, do not force the handoff or invent a failed check.

If the current goal exited **2**, inspect `foundry_status({run,detail:"proof"})`. For a **new source-backed question**, call `foundry_review({run,compare:{directory,receipt,blob,question,source:{commit,file,excerpt}}})`. Use the current exit-2 goal ID, the full current checkpoint commit and a verbatim excerpt from a regular UTF-8 production file in this charter's areas. The blob must already be offered to the requested directory. Ask for operator approval via the tool, not on their behalf. Approval opens only the comparison. The first scout packet delivers the named file or a range at the excerpt; it does not establish what is absent elsewhere. The scout must cite delivered source before proposing a writer. Do not supply `historical`, retry a declined request, or replay the goal. If product or ownership changed, inspect status rather than substituting another revision.

If a disjoint checked output advances the build before a source-backed scout returns its repair, let the owner take a normal turn. Foundry checks the saved report's charter, evidence, scope, ownership, prerequisites and evaluators against the new exit-2 checkpoint. If they still match, the repair continues without another dialog or scout. A changed or unknown input, a newer charter review, or an existing owner can prevent continuation; inspect the review’s reason. A transfer, narrower grant or genuinely new question is a separate decision. Do not replay a declined, unanswered or in-flight request.

To include existing integration files outside the primary directory, add `files:["codec/views/index"]` to that source-backed `foundry_review` (compare) request. The approval names both the primary directory and the exact files; it never grants the parent. Ordinary grants must be disjoint, in charter and outside conserved contracts.

**Transfer from a qualified parent.** Read `productOwnership`, `productPin`, `outputs` and the latest goal/checkpoint in owner status. If the checker is not `retain-except-transferred`, prepare an exclusion-aware checker-only commit and request separate [product repin approval](#evaluator-repinning) with `ownership:"retain-except-transferred"`. Wait for the same-bytes recheck and its **fresh exit-2 goal ID**. Do not assume an `exact-files` checker understands exclusions.

On operator direction, request `foundry_review({run,compare:{receipt,blob,question,directory,files,source:{commit,file,excerpt},transfer:{from,candidate,to}}})`. `from` is the included qualified parent ID, `candidate` its full `outputs[from]` commit (not the product commit), and `to` a new grain ID. The primary subtree and exact regular files must all be strict descendants of that parent's directories, in the same charter, unchanged from its included version, outside previous transfers and conserved paths. Resolve active consumers of the parent or transferred evidence, outstanding parent calls and any other overlapping reservations first. Do not cancel them. Other checked consumers keep their original input pins.

The **transfer approval** names the paths, old pin, new owner, product and goal; approving a checker does not approve this operation. The scout must cite the approved source and return that exact receiving ID and grant without replacing or depending on the donor. Only then does Foundry change ownership. The original parent keeps every other path, including future siblings. The receiver needs a fresh component receipt and changed bytes need fresh product and goal checks. An unrelated join may run before the receiver is included: its paths have no repairable output in that join, not the parent as a fallback. No approval retries, release verification, old writer or old goal replay are implied. Ordinary repartition and whole-package reuse cannot revoke these grants; a conflicting moved target is reported rather than dropping either owner.

For a **previously observed step** instead, only when the immediately preceding goal exited **1** on the identical checked product and its observed failure is not contradicted by the newer receipt, use the current goal ID as `receipt` and add `historical:{receipt:"<earlier check ID>",step:"<stable identifier>"}`. Use the journey or step identifier from the failure, not a failure-only phrase. If the new output mentions it, inspect that evidence instead. The scout receives both observations; an omitted step is neither a fresh failure nor a pass.

Report what actually happened: a note is queued context; `reviews[].iteration` is a review request. For `writing` nodes, owner `writerAssignments` counts bindings, not running sessions. A `bound` writer owns its assignment even if idle; use its original session for a handoff. `unconfirmed` means the original launch is uncertain: use [existing writer recovery](#recover-an-existing-writer), never a replacement. `pending` has no confirmed binding yet. Foundry does not measure session activity. A writer's `preview` is a draft for one focused comparison, not a passing release. If the implementation, target and observation are unchanged, stop comparing. Qualification still requires both checks on the exact joined commit.

### Checkpoint an independent subset

After a signed exit-1 observer, a quiescent owner can request **one non-release checkpoint**. This does not repair the held work. First read `foundry_status({run,detail:"proof"})`. Use `target` (the full target commit), the latest passing `products[].check`, its settled `goalChecks[].id`, and the failed observer's component check ID. For **each** proposed published output take its exact `{grain,candidate,component}` from the node's `grain`, `checked` commit and `check` ID. A green component or empty `requires` is not proof of independence.

Build an `evidence` record for each selected check **and** each of the original failed restoration, negative pair, negative observer and passing retainer checks. Each record is `{component, stages:{component:[note],generated:[note],package:[note],runtime:[note]}}`. Start at that check's actual evaluator. Follow its build rules through generated inputs, packaging and runtime consumers. A note looks like:

```json
{"file":"build/check.mjs","excerpt":"readInputs(\"inputs.json\")","inventory":{"file":"build/inputs.json","keys":["library","sources"]},"reason":"The library compile action consumes these sources, not the separate test target."}
```

`excerpt` must be verbatim at the component commit. The inventory must be an **existing authoritative JSON build input list**, unchanged between the observed assembly, prior checkpoint and proposed checkpoint. `keys` selects the array in the manifest (`[]` for a top-level array). Its entries are repository-root-relative files, recursive directory roots, or bounded `dir/*.ext` selectors. Foundry expands these on the exact trees, including newly added matches, and checks modes and contents. Use a genuine empty inventory only where the cited rule establishes that the stage has no additional inputs. Include notes for every transitive rule, connected to its consumer. Do not create a retrospective manifest or supply a hand-written list. Source snippets, an unenforced manifest, unbounded dynamic reads, or a screenshot of a passing smoke test do not suffice. If the pinned build doesn't provide complete supported inventories, **leave that output held**.

Only on operator direction, use `foundry_checkpoint({run,target,checkpoint,goal,observer,selected,evidence})`. An invalid member rejects the whole request. Review the actual sources and **the entire diff from the original checkpoint to the proposed assembly** before approving the exact batch. Foundry verifies Git and signed ledger facts; it cannot establish that a general-purpose build script obeys its manifest. Decline if the sources do not establish completeness on both sides. No dialog answer is implied by choosing this policy.

Re-read proof. `independentCheckpoint` retains the original hold and links it to `product` and, after a pass, `assessment`. A failed or incomplete product leaves the old checkpoint and every published pin untouched. A passing product includes only the approved outputs alongside the original checkpoint and gets one fresh goal check. Even exit 0 describes only those bytes: `qualified`, `qualification` and `handoff` remain null. The target does not move. The failed observer, its predecessors and the pending retaining output stay on their original evidence; don't replay them or use this goal to authorize cleanup. Resolving that hold requires separate future authority on the then-current product.

For an already-bound, same-directory handoff after `writer-cannot-repair`, `foundry_correct({run,grain,review,worker,clause,file,excerpt})` accepts the assigning review's retained predecessor component instead of requiring an offered comparison blob. Cite a regular file in the grant at the reviewed product. This requires a distinct native approval; it removes one unique clause only. Direct the same writer to read status before proceeding. It neither replays the old check nor changes the binding, evaluator or read permissions.

If the operator wants to **reuse an exhausted failed component**, offer the correction to its directory and use `foundry_grant({run,reuse:{grain,check,candidate,blob}})`. Take `grain`, `check` and `receipt.commit` (the `candidate`) from the blocked node, not the goal or product receipt. Approve only the named candidate directory and correction on the displayed checkpoint. Foundry binds a new writer in the same run; `nodes[].reuse` identifies its reservation and original failure. It cannot resubmit identical bytes, reopen the old writer, or inherit any pass. A later disjoint product is allowed if the reviewed inputs still match. If a join is in flight, let it settle and inspect status; never replay an uncertain or declined request, start a replacement outside Foundry, or use this for unrelated work in the same directory.

For `sharedBlockers`, distinguish the one observed failure from its `blocked` dependent journeys that never ran. The evaluator can report these automatically with `FOUNDRY_BLOCKERS`. A `Foundry escalation` means no repair owner: inspect the exact receipt, latest review and any directory or permission hold. Don't start parallel writers for that directory. If an older current unmet goal has a verbatim diagnostic and a known dependent count but no structured record, the owner may route it once with `foundry_attribute({run,receipt,id,directory,blocked,excerpt})`. A later exact step pass verifies the fix, not the skipped journeys.

`sharedBlockers[].schedulingPass` names a later goal receipt that answered the historical step for scheduling. An exact labelled pass paired to the owner's earlier gap can leave the legacy row `awaiting-verification`: don't commission a stricter observer to change that label. A matching structured pass can verify the step even on exit 2. Neither is a release verdict. A generic baseline success, empty gaps list or omitted journey cannot retire an unobserved defect.

If a later checkpoint carries a gap but not the original diagnostic, queue the original receipt for normal review: `foundry_review_note({run,squad,receipt,question})`. Copy the exact goal check `id` from owner `foundry_status({run,detail:"proof"}).goalChecks`. The ID is sufficient even for large output. Optionally include a verbatim `excerpt` to point at a particular observation. Distinct notes may queue for the same squad. Check `pendingReviewNotes` and the receiving review’s `note` and `otherNotes` before resending. A note does not replay a review, assign a writer, or turn an earlier failure into a fresh observation.

### Charter questions

A missing diagnostic is not an owner decision. Scouts and researchers get the retained goal output for the reviewed commit. If that does not answer a factual question, Foundry uses authorized research when available; otherwise the unknown stays in status, not in an owner dialog. A combined test failure is not a verdict on every component.

A current `needs-decision` identifying a product choice or external action goes to the owner once. `presenting` means the dialog may already be open. A clarification goes to one fresh review of that charter at that revision; it cannot authorize permissions, edits to the brief, or new checks. A dismissed or stale question stays in history. A writer's native request stays in its own session with its own request ID; do not answer or relay it as a charter decision. To conserve a useful answer for future runs, have the operator review a change to the charter or a boundary file with its rationale and source review. Commit and authorize the revised brief separately; chat is not policy.

If the owner lost a dialog on reload, status alone will not reopen it. **Only on the operator's explicit request**, pass that question's `recovery` object unchanged to `foundry_clarify` in the original owner session. The operator enters their answer in the replacement dialog; never supply one for them. This replaces only the named presentation of that review. A late reply to the old dialog cannot overwrite it. If the question or presentation has changed, read status rather than retrying.

If dialog delivery fails, status gives the owner a recovery object for the failed presentation. Use that object only on a new explicit request. A dismissed question has no recovery object.

## Pause and resume

Only the owner pauses with `foundry_pause({run})`. On an explicit `/foundry resume <plan>` in the owner session, call `foundry_resume({source})` directly: `catalog` means `.foundry/catalog.json`, or use the exact requested `.foundry/...` path. Do not run the start helper, change the checkout, or substitute `foundry_start`. Resume resolves the owner's source in the existing ledger, never from a draft or a replacement plan at `HEAD`. If more than one owned run used that path, supply the intended `run` ID as well. Resume never creates a run. For an active run it can retry missing external evidence, recover interrupted discovery, or claim a never-issued writer launch reserved by a published writer. Prepared, held, refused, issued and uncertain native calls stay with their issuer.

Changing a product requirement is not a resume. For an explicitly reviewed change to an evaluator or a mixed descendant target, use [evaluator repinning](#evaluator-repinning); a different plan needs its own authorization.

<summary>The reader changed, a target moved, or permission is on hold</summary>

If Foundry says its installed reader changed, reload extensions **in the session that reported it**, then read status for the same run. A writer submits only if its original token is still writing with no check pending. Don't resume the run, replace the writer, or retry a pending submission.

If a **bound scout** ended with Foundry's reader-change execution error before it recorded a report, the reloaded issuer observes the original workflow's terminal result. On a normal scheduling turn, that issuer or the owner can automatically reserve one fresh scout for the same still-current review, including a failure already recorded before the upgrade. Look for `retryOf` on the new review. Completed sibling reports stand. A newer charter review or checkpoint supersedes the old question; absence of a replacement there is intentional. No rereview command, goal replay or run restart is needed.

When the target advances during automatic checkpoint discovery, keep the original issuer and reservation. Resolve a managed-policy hold in its named issuer and keep that session open: its observer returns to dispatch without an owner command. An explicit pause or a legacy pause without a structured cause still requires operator-directed resume. A `release.workTarget` identifies the old target for checkpoint work; `release.target` is the live branch tip. Scouts and their writers use only the original checked product. An unrelated merge is included in a fresh product and goal check. If conserved inputs changed, component results can publish on their original pins, but the new target cannot integrate or qualify under the old contract. Status lists the conflicting paths. Do not restore files, adopt new evaluators, replay the goal, or start another run as part of resume.

An uncertain writer start or cross-session notice keeps its original call ID. While the run is active, the original issuer watches native completions and re-reads its own history with backoff, including after reload. If a matching receipt becomes available, work continues without another turn or `/foundry resume`. A refusal remains a refusal. Missing or conflicting history never permits another start; an operator pause is not cleared by a late reply.

The same permission wake covers an eligible saved scout report and an owner question that has **never** been presented. The owner revalidates the report’s inputs or presents the original question once. It does not invent an answer, repeat a dismissed or unconfirmed dialog, or spend another scout assignment.

On a settled exit 1 or 2, a descendant target need not strand work on the signed checkpoint. With no conflicting join, ownership or permission hold, the owner can use the existing `correct` for the original task, `foundry_check` for a separately requested observation of a signed stopped component, or `foundry_grant({run,repairBaseline:{grains:[...]}})` for a bounded group of original missing-input writers with unchanged directories. Each operation retains its own approval, input and capacity checks. `inspectBaseline` alone grants inspection, not a repair. None integrates or qualifies the changed target.

A session-local Manual hold appears in `pending`: other sessions continue; the original issuer rechecks on its next turn. Don't restart for this. For a managed-policy pause, first resolve the setting in `blocker`. While a checkpoint goal is running or after exit 2, Foundry can prioritize a previously named blocker and investigate other charters with unfinished surveys in parallel. `reviews[].lead` distinguishes an issued `pending` goal from a `missing` receipt. `priorReview` identifies the independent charter's own evidence or packet refusal. No manual comparison or release retry is needed. To retry a missing release observation itself, supply it and resume the same run. Preserve receipts and worktrees. If a native session route is definitely unavailable, execute the exact `prepared` call once in its issuing session. Never repeat an issued or uncertain start, treat a queued message as completed work, or bypass a permission hold.

</details>

<summary>A check or scout stopped without the evidence needed to proceed</summary>

For a **confirmed synchronous launcher failure before claim** or a **signed goal with `exit:null`**, correct the environment first. On explicit operator direction, inspect `foundry_status({run,detail:"proof"}).checkRecovery` and call `foundry_check({run,recover:{check}})` with the exact current check ID. An unknown launch, a modern claim without an outcome, a refusal, an expired contract or a product-pin upgrade's own verification cannot use this route.

Use the original component ID and full checkpoint commit. Approval runs the real check in a disposable export; proof status links the signed outcome in `checkRecovery`. Do not batch mixed code, partial directories or external historical helpers. Review the exact files and subtree IDs in the approval. Watch `deliveries` for serial component results on the combined commit, one product check and a separate goal. The board's **Passed on build · not integrated** is not permission to skip these checks.

Use the old goal reservation ID. Foundry verifies the matching native shell-completion notification and `read_bash` result for the decoder failure, then asks for approval. A missing or conflicting record leaves the run alone. `retired` means infrastructure failure, **not an evaluator verdict**. Normal integration and checks apply to the new product; no writer resubmission or old-goal replay. This is not a workaround for a running check, a refused call or a missing external observation.

Full native workflow slots are a queue, not a pause: the issuing session retries automatically. A verified provider disconnect gets one automatic continuation on the same native ID and inputs. Only on explicit direction there, use `run_dynamic_workflow({resumeFromRunId: "<original ID>"})`. Do not change limits, retry a cancellation or refusal, or launch a replacement. Older ledger protocols are not migrated: preserve the old clone and use a fresh clone for a new run.

For a **reported source comparison rejected because its approved file was not delivered**, use the original review ID without changing the offer, excerpt or question. The replacement scout uses the existing source approval. Foundry preserves the blocked report and verifies that the corrected packet delivers the pinned file or a citable range. Look for `reviews[].retryOf` to confirm the replacement; check the node's worker ID separately before saying a repair has started.

### Recover an existing writer

1. In the **existing writer session**, call the ordinary App `get_session` on itself, then `foundry_claim({run, token})` with the token from its own original kickoff, or use `{run, grain}` if known. Do not send the token to anyone. `awaiting_issuer` means its original startup path and generation, first issuer-sourced kickoff and App creation edge match. It is not bound yet.
2. In the **original issuing session** (see `pending.issuer`), check status for `pending[].claim: "awaiting_issuer"` and call `foundry_claim({run, grain})` using that row's grain. This does not require a cross-session message. `bound` requires its unique original external request, matching arguments and UI dismissal, no conflicting native completion or refusal, and the existing linked worktree at the original parentless generation.
3. Only in that writer, after its helpers finish, use the ordinary `foundry_submit` with its original token. Neither claim proves the component passes. If either proof is missing or conflicting, stop; do not recreate the session, paste an identity or prompt as evidence, or edit the ledger.

## Evaluator repinning

**Goal (default).** Omitting `kind` selects only the final goal evaluator. It never opts the run into exact-file comparisons.

Only on a direct operator request in the active run's **owner session**, read status for `goal.pin`. Prepare or identify a separately reviewed evaluator-only commit based on that pin, **off the run's target branch**. Do not commit working-tree changes without authorization. Inspect the complete diff, including additions, deletions, and helpers shared across plan directories. Reject changes to what counts as a pass; path checks cannot establish that the requirements are unchanged.

Call `foundry_repin({run, from, revision, files})` with both full commit IDs and the exact changed paths. The operator reviews the change and clicks the approval button in the owner session; there is no checkbox or text field. Declining or dismissing ends this request: do not retry or ask again without fresh operator direction. No recheck starts; unrelated work can continue. If the run is blocked, report the existing blocker. A stale approval cannot change the pin. Do not answer that dialog for the operator. Reload any participating session predating the reader-version guard before repinning.

The runner applies only the reviewed evaluator changes to a temporary export for **goal checks only**. An issued or uncertain check keeps its original reservation. Once it settles, Foundry checks the checkpoint under the new evaluator, preserving product bytes, writer tokens, prior receipts and the original contract. `goal.pin`, `evaluatorChanges` and `goalChecks` in owner status distinguish the approved revision from checks already issued. A refusal or permission hold is not bypassed. No pause, resume, or writer resubmission is needed.

Do not continue a paused scout from a superseded evaluator pin. Foundry releases its slot when the native stop is confirmed; an unknown outcome is not confirmation.

If the approved pin is waiting on a superseded goal, `blocker` names the original reservation and issuer. `uncertain` is not evidence that the evaluator has stopped. Normally let it finish. If the operator explicitly asks to interrupt it, first match the live runner to the exact checkout, run and reservation, and its direct evaluator child to the exported check. If that identity or safe cleanup of its subprocesses cannot be established, stop. Terminate only the verified obsolete evaluator, **not its Foundry runner**: the runner must record the interruption. Verify cleanup, the old non-passing receipt and one new reservation on the same product with the approved pin. A missing receipt is not a reason to replay the check or edit the ledger.

**Product checker (separate opt-in).** On explicit operator direction, use `foundry_repin({run,kind:"product",from,revision,files})`. Read `productPin` in owner status, not `goal.pin`. Review the complete committed diff from that exact pin off the target branch. Only the `.foundry/` product checker and private helpers under `<checker-path>.d/` may change, never a conserved file or writable path. Verify the checker handles `FOUNDRY_OWNERSHIP` (including exact files) without changing what counts as a pass. The product-specific consent names the checked product, prior passing reservation and opt-in. It does not grant a writer access to any file.

The original target must still have this exact applied checkpoint and a settled exit-1 or exit-2 goal. Resolve live or uncertain calls, active reports/questions, joins and writer obligations first. A blocked or repeated node, an obsolete undispatched notice, or a superseded question with a historical `presenting` marker alone does not require cleanup. Preserve the original evidence. **A bound writer is not released by native idle or by a failed check.** The original writer may submit genuinely repaired work under its existing grant. Use `missingInput` only for an actual missing input; use the status-provided `cannotRepair:{check,reason}` only for an eligible inline exit 2 when the assignment permits no further repair.

When neither a genuine scoped repair nor a missing input exists, the **original writer only** may have `relinquish.check` in its own status. Use the [writer stop](assignments.md) there: the owner cannot relinquish on its behalf. This leaves the numeric verdict and checked bytes intact. If no supported stop is offered, keep the binding; neither idle time nor a later observation supplies one.

Approval records `productEvaluatorChanges` and reserves one fresh product check on exactly the prior bytes and output pins. Its original checkpoint and goal remain history, not authority. No comparison or release can proceed on the old pass. A passing recheck triggers a fresh goal on the same bytes with its **own** goal pin. A non-pass, permission hold or uncertain check does not release the gate or trigger repairs. Do not retry it by resuming or using ordinary check recovery. Future comparisons need fresh evidence and normal approval. Reload participating sessions onto the deployed reader before upgrading.

### Mixed target adoption

Use `foundry_repin({run,kind:"target",from,revision,files,checkpoint,goal,acceptance})` only on direct operator direction. `from` is `contractPin`; `revision` is the full live descendant target SHA. `checkpoint` and `goal` are the last passing product **check ID** and settled exit-1/2 goal **check ID** on the same product. Resolve outstanding writers, calls and ownership conflicts first. Published components may be included; a missing-input stop is not an included output.

`waiting` is a queue, not permission for a writer to submit. If the first ordinary component returned a signed exit 2, no repair was issued, and neither the checkpoint, a consumer nor a special ownership grant uses that candidate, target adoption lists its grain, commit and check for retention. Approval leaves the old repair blocked on the superseded contract: its candidate, preview, prior tree and receipt survive. The joined product keeps the base directory, if present, not the unverified candidate. Do not ask the writer to relinquish a grant it never received or rerun an external observation to clear the queue. Other waiting work and issued repairs still hold adoption.

Review the union of the diffs **to `revision` from each of** `contractPin`, `productPin` and `goal.pin`, restricted to the plan's conserved files and all of `.foundry/`. Name every added, modified and deleted path in `files`. Inspect shared helpers, old overlays missing from the target, and operator edits outside that list that overlap owned outputs. The activated plan must be unchanged. In `acceptance` state the actual difference in what passes and what the new charter permits prospectively; do not describe changed requirements as an evaluator-only fix.

For `Concurrent modification since checkpoint`, first distinguish a squad's area from an included writer's grant. A reviewed merged blob on a descendant branch is not sufficient: Foundry compares three trees, not commit ancestry or merge hints. On operator direction, the same target approval accepts `resolutions:[{file,mode,base,checkpoint,target,result}]` **only outside included output grants and conserved files**. These are full Git **blob** IDs: the file at the prior product's target, the checked product, the live target, and the expected resolved file. Mode is the common `100644` or `100755`. The result need not already be a Git object or a commit on `main`.

List every nontrivial index conflict, not just the first one reported. Foundry extracts the changed whole-line span from base to target, applies it verbatim once to the checkpoint, and verifies its inverse and resulting blob. Ambiguous, binary, missing, mode-changing or additional unlisted paths do not qualify. The approval shows the exact replacement, all blob IDs and joined commit. Declining changes no run state. Original input checks and ownership still apply; if the file is covered or a new writer cited stale bytes, stop rather than deleting the file from the manifest. After approval, inspect `productEvaluatorChanges[].resolutions` and new component, product and goal results on the assembly, not the old writers' receipts.

The goal executable is invoked **without arguments**. Verify that its bare entrypoint evaluates the full promised outcome, not a repair or checkpoint lane. If it doesn't, select a separately reviewed fix to the product's own entrypoint. A manual invocation, secondary lane or old goal pass cannot qualify the join.

The native decision shows both approved evaluator pins, the target, exact assembly, outputs and change in acceptance. A real operator confirmation is required in every mode. It neither expands file ownership nor retroactively amends a writer's charter. Foundry preserves the operator commit as parent and reruns each included component, the product, and then the goal on the joined bytes. Inspect the new receipts: a failed component stops before the product evaluator or goal, a failed product stops before the goal, and exit 2 is not qualification. No branch movement, automatic retry or release follows from approval alone.
